# auto-the-spire 协作约定

本文件适用于 `docs/` 及其子目录。子目录若有自己的 `AGENTS.md`，在其范围内同时遵守更具体的约定。

## 当前接手与维护

[docs/README.md](README.md)是唯一文档总入口。[主清单](review/tofix/README.md)维护阶段大目标、稳定任务ID、P优先级、认领/依赖/完成条件和完整ENV/W范围。管理与交接格式见[约定](design/post-core-agent-assignments.md)。

维护文档时，按以下边界更新：任务提示词只导航，设计/契约只定义方法与范围，records 只保存带日期证据。按用户2026-10-15的人类审阅要求，主清单总览表唯一维护任务状态、优先级和剩余工作；同页可展开详情维护认领、依赖、接手步骤及完成条件。原语子任务和ENV/W整体范围各在对应章节维护，不复制第二套状态表，不追加逐批流水账。

负责人按用户授权压缩当前入口时，必须保留完整任务范围与原历史证据。执行者仍不得擅自删减 W 或替换主清单。

本目录所有作者必须执行根[任务与文档管理强制规则](../AGENTS.md#任务与文档管理全仓库强制)。只修改文档时，也不能另建当前任务表或恢复历史派单。负责人维护范围、优先级和关闭结论；执行者只更新本线任务及证据。规范、工作包和报告使用稳定任务 ID 关联，状态仍只维护一处。

将报告移入 records 后，标明原日期与当前任务归属，并修复指向该报告的链接。对已修复的窄缺陷，另列关闭范围。

纯文档交付前，运行 `python tools/doc-check/check_docs.py` 和 `git diff --check`，报告实际结果及未运行项目。

## 写成可以接手的交接

交接开篇说明本包交付的用途，给出主清单对应项和必要工作包的具体入口。详细实现记录之前，先写接手后的第一步、前置条件、预期结果与原完成条件；本包已交付的部分也要明确，避免重做。任务 ID 配任务名称，长日志留在证据目录。

已交付能力、实际验证和未验证范围分别说明，当前任务状态只链接或回写主清单。带日期报告中的“下一步”是当时建议，接手时重查当前清单。没有待续工作时写明本次维护完成，不创造新的派单。

交付前用正文及其直接链接进行接手自查：读者应能定位目标与当前状态、可复用成果、第一步、完成条件与验收者、阻塞/未验证及唯一维护位置。缺失必要信息先补来源；自查不能称为独立读者验证。

已安装的用户级 `$auto-the-spire-handoff` 提供交接模板、整理方法与接手检查。它沿用本项目 tofix/records 和任务权限，不另设状态表；普通措辞修订仍可使用 `$nbj-write-clearly`。

## 按 Diátaxis 编写面向使用者的文档

用户要求文档遵循 [Diátaxis](https://diataxis.fr/)。新增或重写使用者文档时，先确定读者此刻要学习、完成任务、查信息还是理解原因，再选择主要类型。两篇首次教程及core入口是当前示范，不要求为分类批量移动历史文件。

| 类型 | 服务的需要 | 写作要求 |
| --- | --- | --- |
| [教程 Tutorial](https://diataxis.fr/tutorials/) | 在指导下学习 | 固定一条可靠路线；写明确操作、可见结果和检查点；减少概念说明；不要在途中让初学者选择方案 |
| [操作指南 How-to](https://diataxis.fr/how-to-guides/) | 完成已知任务 | 用具体用户目标命名；注明适用条件；假定读者已有必要基础，允许实际场景中的判断和分支 |
| [参考 Reference](https://diataxis.fr/reference/) | 查找准确事实 | 按语言/API自身结构组织；提供参数、类型、默认值、范围与错误语义；保持中性描述 |
| [解释 Explanation](https://diataxis.fr/explanation/) | 理解原因与关系 | 围绕概念、背景、设计取舍和后果展开；不把它写成操作步骤 |

一个正文页面以一种主要需要组织；无关类型的长段落迁到相应页面并互相链接。参考资料不能充当首次教程，概念介绍也不能代替实际操作指南。入口页按四种需要导航；AGENTS、任务清单、合同与历史证据仍遵守已有唯一维护位置，不强行改写成四类使用者正文。

教程的操作、文件路径和预期输出须实际走通。按阶段从空目录/初始状态复现，不能只跑预先完成的最终示例就宣称教学路径可用。注明必要SDK、工作目录、步骤的替换/追加关系，以及示例的适用范围；补救提示只覆盖本步常见问题。

结构复核可使用仓库安装的 [Canonical documentation-diataxis skill](../.agents/skills/documentation-diataxis/SKILL.md)：记录页面目标类型与实际内容类型、混入内容的具体位置、对读者的影响及迁移/改写结果。该skill负责分类审阅，不替代技术验证；写作原则以原站为准。修改后执行本文件已有文档检查。

## 按 NBJ Write Clearly 修订技术表达

技术文档采用 [NBJ Write Clearly](https://github.com/daniel-p-green/nbj-write-clearly) 的清晰写作原则。该 skill 整理了 [Google 技术文档写作指南](https://developers.google.com/style)的常用规则，是非官方实现。已安装时，可用 `$nbj-write-clearly` 进行编写、修订或只读审阅。

Diátaxis 帮助作者选择文档类型；NBJ Write Clearly 帮助作者表达内容。应用时，用户要求、事实与技术标记、本项目约定优先于通用风格建议。中文文档保持中文，不套用英语语法和标点规则。

编写或修订时，依次核对：

1. 开篇说明读者要完成什么，以及本页适用于什么范围。
2. 每段围绕一个意思展开，重要结论先写。需要采取行动时，明确执行者和动作。
3. 将前置条件放在操作前。按顺序执行的步骤用编号，平行事项用列表，需要比较的字段用表格。
4. 首次出现的必要术语说明含义，同一概念使用同一名称。链接文字说明目标内容。
5. 保留命令、代码、路径、API 名称、内容 ID、版本、数字、引用和限定条件。区分设计目标、解析器接受、实际加载及行为验证；旧状态注明日期，当前状态链接主清单。
6. 删除不提供信息的开场、重复结论和夸张断言。不要为压缩篇幅删掉验收范围或未验证项。

正文已清楚、准确且一致时，停止润色。历史证据保留原文；只读审阅仅报告问题。风格检查不能替代技术验证，也不能据此宣称已完整符合 Google 指南。

## 目录说明

本目录存放 `auto-the-spire` 的项目文档。
`review/tofix` 存放当前问题清单及待整理的阶段交接，`review/records` 存放历史证据，`review/archived` 存放有关闭依据的缺陷报告，`review/deprecated` 存放因范围变更不再适用的报告。
2026-10-03 整理约定：`review/tofix/README.md` 是唯一当前整改/待决清单。提交新交接时，先按根约定交到 tofix，按阶段合并小批次；不要为每个原语单独新增报告。负责人审阅后，将开放项并入清单。

`review/records/YYYY-MM-DD/` 保存交付、部分交付、来源审计和历史规划证据，`review/records/README.md` 登记原报告与当前事项。移入 records 不表示问题已修复；只有有关闭依据的缺陷才转入 archived。实现者按清单认领并补证据，不能把旧报告里的“未开始/下一步”当作新派单。
执行者更新主清单时仅补对应条目的认领、进度和证据；不得清空、删减W项、移走主清单或用最小指针版替换完整任务定义。范围、优先级和关闭结论由用户/规划者维护；发现内容丢失先保留当前版本和证据，再交负责人恢复。阶段报告的RESUME HERE只定位该执行线，不取代全项目待办入口。
`dsl/` 里存放关于dsl脚本如何编写与如何工作等行为的文档介绍，并且对dsl版本进行区分，游戏内容语言为 `dsl/0.0.1/`，通用 core 基础语言为 `dsl/core/0.1/`，DSL 规则库与作者配置层为 `dsl/core/0.2/`，默认作者入口是 `dsl/core/README.md`。
`design/` 里存放关于项目设计相关的报告，分为`design/net-the-spire`、`design/core-the-spire`、`design/mod-the-spire`、`design/ai-the-spire`这四个目录。
`design/spec.md` 描述项目整体上的specification，各模块的specification放在各自的目录里；跨模块的项目级报告（源码审计、阶段评审等）直接放在 `design/` 下。
