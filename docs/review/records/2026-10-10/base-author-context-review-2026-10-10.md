# Base 内容编写的低上下文自审

日期：2026-10-10。归属[ENV-T06](../../tofix/README.md#env-t06)，关联[T05](../../tofix/README.md#env-t05)。按用户要求由 Codex `/root` 自审此前的核心编排重构；本轮只读生产代码、在独有audit目录执行探针并维护复核记录，未改生产规则或派发DSH。任务状态与后继认领只维护主清单。

## 结论

**组合已有原语的新卡可以局部编写；所有新卡、Power和新机制都能用极少上下文完成的目标尚未达到。** 上轮实现已经隔离付款、目标、事件历史、牌区及结果区，让作者无需重复编排；但Power仍按内容ID放行，部分旧校验与新共享能力冲突，升级实例的变量转换也没有完整契约。不能用15个短文件或回归全绿证明全内容类型的心智负担已极大降低。

| 内容类型 | 必要开发路径 | 本轮判断 |
| --- | --- | --- |
| 用已有叶效果组合新卡 | 一个 `.spire` 的普通/升级块、相近例子、工具命令、独立行为预期 | 已有短路径；无须修改C#或读整套出牌流程 |
| 新卡使用已加载Power | 明确Power ID及作用对象，再组合 `applyPower` / 攻击 | 实跑可行；引用语义仍须按需求核对 |
| 新卡声明生命周期/变量升级 | 还须理解前端hook校验、实例升级与初始化差异 | 未达标；发现拒绝和行为缺口 |
| 新增DSL叶效果/查询 | 源读取、领域节点、编译分支、状态/命令绑定及检查 | 比此前更有边界，但仍需多处知识，不能称“只写DSL” |
| 新增Power | Power前端、ID放行、字符串效果降级、组包触发点、施加/移除/寿命及独立检查 | 未达标；同已有行为的新ID也被拒绝，无独立作者工具 |

常规卡作者可用[30行例子](../../../examples/base-card-mod/two-hits.spire)、[94行modding指南](../../../design/mod-the-spire/modding-guide.md)及[18行工具说明](../../../../tools/base-spire-dev/README.md)进入，共142行/5974字符，另加任务需求和必要源片段。这是可用文档路线规模，不是模型token测量。审阅由同一作者手工演练，未做独立读者或模型冷启动实验；实际证明是只改DSL即可加载执行，不能由此估算所有开发者的理解成本。

## 实跑与可复核发现

先重新构建作者工具，确认当前生产源码及依赖。命令/退出码/JSON/耗时见[探针结果](../../../../.audit/base-author-context-review-2026-10-10/results.json)，[脚本](../../../../.audit/base-author-context-review-2026-10-10/review.py)包含独立预期断言。内容与源码行数/字符数/哈希见[读取规模](../../../../.audit/base-author-context-review-2026-10-10/readset.json)。

### 1. 常规卡的短路径成立

独立命名空间 `context-review` 的 Combo 普通按2点攻击→3格挡→5点攻击执行，实际扣7血；升级3点攻击→4格挡→8点攻击，实际扣11血。PowerCombo先施加2/3层已有Strength，再攻击3/4，实际扣5/7血。两份新DSL的check、普通及升级play共6次调用均rc0，内容实际创建实例及出牌，无生产C#修改。

最后执行的多数作者调用为0.35～0.38秒；重建后首个check为2.10秒。这里包含进程/组包/受控会话启动，属于本机Debug观察，不能宣称Release训练吞吐或地图性能提升。

### 2. Power仍被ID耦合阻断

位置：`SpirePowerSource.cs:256～270`。`RuntimeImplemented` 按ID末段放行，没有按已实现的语义判断。原FeelNoPain声明“消耗后每层给1格挡”可降级；只把名称改为新包的QuietArmor，保持同一触发和效果，得到 **1声明/1解析/0降级**，原因仅是 `quiet-armor` 不在白名单。运行时 `TriggerChain` 已按定义/Trigger/TriggerEffect处理该类模式，但内容作者仍被迫修改前端实现表。

另一个名字反例：`package review-mod { power FeelNoPain { ... } }` 被默认KnownIds映射成 `base-spire:feel-no-pain`，不会保留新命名空间。调用方显式ID表可影响映射，然而新叶ID仍遇到上述白名单。不能把复用原版名字当作mod扩展办法。

[Power前端三组输出](../../../../.audit/base-author-context-review-2026-10-10/power-frontend.log)分别为原名1降级、新名0降级、异包同名1降级但冒用base ID。作者工具也明确拒绝 `power` 声明，rc2；没有低上下文的Power检查/触发入口。

这是本次最高优先级的结构缺口：`AuthorPower.TriggerEffect`仍是 `gain-block-per-stack:N`、序列分隔符等字符串；组包器内各事件链自行拆解。新Power作者必须理解前端与多个结算站点之间的协议。Power前端1655行、组包器4185行；不要求把这些文件全读完，但接口信息和实现位置仍散落其间。

### 3. 旧hook校验阻止合法组合

位置：`SpireCardSource.cs:794～800`。声明onExhaust、没有自身exhaust关键词的新卡被拒绝，理由仍是“没有别的路径消耗它”。共享 `CardPileProcedures.Move` 在移动到Exhaust时会执行afterExhaust；forEach消耗和自动出牌forceExhaust已存在，前端假设已失效。

只改变是否带exhaust关键词的两份相同HookProbe，结果分别 **1解析/0降级/rc2** 与 **1注册/rc0**，见[hook结果](../../../../.audit/base-author-context-review-2026-10-10/hook-results.json)和[脚本](../../../../.audit/base-author-context-review-2026-10-10/hook_probe.py)。此处验证源拒绝及对照注册，未绕过前端执行被拒绝的内容。新能力不能自由组合，会迫使作者进入解析器排查，也继续阻断DrumOfBattle。

### 4. 共享升级尚未拥有完整变量迁移语义

位置：`Orchestration/CardDefinitions.cs:50～74`。Upgrade只改Upgraded、Cost、Amount、PowerStacks。新卡声明 `Charge default=2 upgraded=9`，通过当前正式前端降级，将它与真实Armaments组成受控牌组并升级该实例，得到：升级标记false→true，费用2→1，Charge仍为2。

[实际Armaments升级输出](../../../../.audit/base-author-context-review-2026-10-10/shared-upgrade.log)来自同一Engine/正式卡源，seed20261001，Session保持Running。这里需要定义“变量升级怎样转换已有值”的契约：初值差额、固定重设或保留实例成长应明确区分，不能简单把所有当前变量重设为升级初值。现有DSL只表达两个初值，作者没有自足的转换接口。本例对固定Charge要求升级到9，当前流程做不到。

### 5. 作者工具的升级验证范围不足

位置：`tools/base-spire-dev/Program.cs:51～52`。工具只设置Upgraded标记。CostProbe声明普通2费、升级1费；两种play都rc0并分别执行普通/升级牌体，但升级仍实际扣2能量。这个限制已在工具文档披露，并不代表正式升级费用也错误；上节真实Armaments的费用迁移正确。

它意味着作者工具不能完整验证刚写的新卡，变量/费用/入场hook仍要另写C#夹具或自行改实例字段。低上下文作者入口应提供按同一配方创建升级实例、实际升级已有实例及必要触发事件的受控场景，明确分列两种语义。

## 可行的改良顺序与验收

以下为负责人建议，尚未生产实施，实际排期和认领只见主清单。

1. **先使已有能力可以自由组合。** 修正失效的onExhaust可达性假设；明确变量升级策略并集中到CardDefinitions，使新建升级实例与升级既有实例可分别验证。作者工具复用同一实例配方，避免只置标记。
2. **再把Power迁到语义接口。** 建立类型化Power程序与事件上下文，显式提供owner、来源、事件目标/数值、当前卡、阶段与寿命。按实际可编译的修正/触发/效果能力放行，保留未实现语义的拒绝；不能仅删除ID表就宣称全Power支持。命名空间ID与原版别名分开处理。
3. **让Power复用共享命令并有局部反馈。** 以“消耗后按层数获得格挡”作为首个纵向案例：新命名空间、新ID、事件过滤、叠层/移除、正反触发都能仅用内容文件执行。Power编译器绑定现有伤害/格挡/抽牌/施加能力等过程，事件编排拥有触发时点，叶效果不处理终局。
4. **收敛读取与绑定入口。** 按实际已支持能力提供短参考，覆盖参数/默认值/可用阶段/状态读时点及例子。新增语义仍交完整前端→IR→命令链，但只需要该机制的契约与对应模块；避免另造反射注册器、第二个运行时或卡牌专属旁路。

判断进一步改良成功，应执行两个独立ID但相同语义的内容，保证无需改C#；普通/升级、施加/移除和错误阶段有可区分的检查；作者工具能给出字段及触发结果；开发读取范围和源依据明示。若还需增加内容ID白名单、追读全组包器或手工设置内部字段，仍不能验收“极少上下文”。
