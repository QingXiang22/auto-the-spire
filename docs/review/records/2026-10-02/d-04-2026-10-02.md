## 1. 交付内容

**跨模块入口** `tools/collect/collect.py`：一条命令完成 **有界采样 → 审计 → 汇报**。

```bash
python tools/collect/collect.py --config tools/collect/example-config.json
python tools/collect/collect.py --root <dir> --episodes 5 --workers 2 --resume
```

产物（全部写在调用方给的 `root`，**不进源码树**）：

| 文件 | 内容 |
| --- | --- |
| `records/*.json` | 每个 episode 一条 D-01 规范字节记录 |
| `index.jsonl` | D-01 派生索引（可由记录重建比对） |
| `progress.json` | 进度与 checkpoint 索引：`attempted/written/counts/stop_reason/stop_detail/next_episode_index/`**`resume_from_index`** |
| `audit.json` | D-03 审计（划分/奖励隔离/完整性/计数/偏移） |
| `report.json` | 本次汇报：采集结果、**失败分类**、审计摘要、恢复语义 |

退出码：`0` 采集完成且审计无问题；`1` 审计有问题；`2` 配置/参数错误。

**恢复语义（本批的核心承诺）**：

- 恢复的是**采样进度**，不是游戏中途状态。`report.json` 显式写 `resume_semantics: "sampling_progress_only"`、
  `game_state_resumed: false`、`no_public_rollback: true`；宿主也不支持 `attach`。
- 被中断的那一局保持 `interrupted`（**不**改写成终止或失败），并在 `progress.json` 里通过
  `resume_from_index` 指向**它自己**——恢复时**从头新开**这一局，而不是接着死掉的会话打。
- `next_episode_index` 与 `resume_from_index` 的区别是刻意的：前者是"已推进到哪一号"，后者是"恢复从哪一号做"。

**失败分类**（`report.json.failures`，互不混淆）：

| 分类 | 含义 |
| --- | --- |
| `host_lost` | 传输层丢失/结果不确定；该局保持 `interrupted`，恢复时从头新开 |
| `backend_fault` | 后端故障；不伪装成胜负 |
| `implementation_error` | 实现/配置错误（`stop_reason=error`），带原文 |
| `limit_stops` | 限额停止（`time_limit`/`disk_limit`/`inflight_limit`），带原因文本 |
| `truncated_episodes` | 达到每局步数上限的**显式截断**，不是失败 |
| `unknown_transitions` | 结果不确定的转移数 |

| 退出证据要求 | 检查 |
| --- | --- |

| 进度与 checkpoint 索引 | `restart/partial-record-saved`、`restart/resume-points-at-interrupted-index`、`limits/progress-*`（D-02）；`progress.json` 同时给出 `next_episode_index` 与 `resume_from_index` |
| 失败分类 | `failure-classes/*`：限额停止点名 `time_limit` 且带原因；截断单独计数且写明"不是失败"；中断与后端故障两块语义与计数都在 |
| 可重启监督入口 | `restart/*`：故障注入中断 → `host_lost` + `resume_from_index=0` + 中断记录保留；`--resume` 后从 0 号**从头新开**并采完全部 3 局，`resumed_from.start_index=0`、`previous_stop_reason=host_lost` |
| 单会话长跑可复现 | `entry` + `multiworker`：同一配置两次运行的记录内容身份一致 |
| 多 worker 交错可复现 | `multiworker/content-identical-to-single-worker`（2 worker 交错 vs 单 worker：种子/结束分类/逐步张量摘要一致）、`both-workers-used` |
| **恢复的是采样进度，不恢复 NoSL 游戏中途状态** | `restart/resume-does-not-restore-game-state`（两处显式 false）、`restart/resumed-episodes-start-fresh`（每条恢复记录的 `transitions[0].index == 0`，即从开局开始）、`restart/interrupted-not-rewritten-as-terminal`、`restart/audit-excludes-interrupted-from-usable`（中断局不计入可用样本） |

## 3. 本轮修掉的真实缺陷

1. **中断后复用已死的 worker 连接**：一条连接被中断（宿主被杀）后，Collector 仍把它交给下一局使用，
   于是恢复运行在死管道上立刻失败，并被归成 `error`。修复：中断后**替换该 worker 的连接**
   （`_replace`），并保证清理容错。
2. **准备阶段的传输失败被误判为实现错误**：`prepare()`（describe/get_catalog）阶段的 `OutcomeUnknown`
   会逃出 `run()`，被 Collector 的兜底 `except Exception` 记成 `stop_reason=error` + `faulted`。
   修复：兜底前先按 `interruption_errors` 判定为 `host_lost`（实现错误仍归 `error`）。
3. **配置文件的 BOM 导致"配置非法"**：Windows 的 `Out-File -Encoding utf8` 会写 BOM，
   而 `json.loads(read_text("utf-8"))` 直接报解码错。修复：配置按 `utf-8-sig` 读，
   并在检查里固定这条回归（`config/bom-config-accepted`）。
   （这条正是台账里记过的"解析 JSON 必须显式处理编码"同类问题。）

## 5. 未覆盖与边界

1. **不是并行调度**：多 worker 仍是"多个独立宿主进程 + 逐局轮转"，证明的是隔离与可复现；
   真正的并行执行与进程级监督（守护、重启策略、资源隔离）不在本轮承诺内。
2. **进程丢失只覆盖"宿主被杀"这一种**：`restart` 组用注入的宿主丢失；真实的**监督进程自身**被杀、
   机器重启、磁盘写满等情况未覆盖。
3. **恢复不重建已损坏的记录**：若记录文件被截断，审计会报出来（D-03 的"记录不可读"），
   但入口不会自动修复——修数据需要显式操作，不在长跑里自动做。
4. **限额是开发用保守配置**：不写成产品门槛；也没有分布式采样、云部署或远程监听。
5. **采集规模仍是有界小批量**：按 §13 的要求，长任务只跑验证所需的有限实验。
6. 数据划分仍退化（场景簇不足，见 [d-03](d-03-2026-10-02.md) §5）：入口会如实报告，不掩盖。
