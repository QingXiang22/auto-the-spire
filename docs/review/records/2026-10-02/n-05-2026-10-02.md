## 2. 本轮找到并修复的真实缺陷

### 2.1 撤销的已知事实仍作为活实例存在（base-spire）

`ClearKnownCards` / `RevokeKnown` 原来只把事实从 `Known` 区域移除（`RemoveFromCollection`），**不销毁实例**。
事实实例仍然是活体，因此仍然出现在投影的 `entities` 里；net 于是继续把它读成 `known_positions`，而卡牌早已
离开隐藏牌区 → `card_ref ⊆ visible_members`（I-29）被违反。

- 发现路径：`V-03 已知位置在真实链路上保留/失效` 在"结束回合抽到那张牌"后的投影里报
  `[I-29] snapshot.piles[e5].known_positions[e9]: 已知位置的 card_ref 'e9' 不是 visible_members 的子集`。
- 判定方法：用提供方判定工具 dump 出 `facts=[20 card=#9 pos=0 edges=[]]`——**同一个事实实例既没有授权边、
  又仍然是活实例**，直接定位到"撤销只移除成员、不销毁实例"。
- 修复：`clearKnown` / `revokeKnown` 改为 `ClearRelation` + **`Destroy`**（`Destroy` 同时清理成员与关系）。
- 加固：切片检查 `B-04 drawing a known card revokes its position` 增加断言
  "被撤销的事实不得作为活实例生存"；覆盖表把"撤销必须销毁实例"写成**包侧纪律**。
- 为什么以前没暴露：H-01 之前"已知卡"是定义 ID 型事实，位置作为普通字段发布，过期事实只是显示旧位置，
  没有跨结构不变量能抓到它；I-29 正是为这类"看似合理、实际失效"的知识而存在。

### 2.2 目录的 `entity_kinds[].id` 用了引擎内部 ID（net）

`CatalogProjector` 原来用 profile 字典的**键**（引擎 qualified id，如 `base-spire:Player`）作为目录的
`entity_kinds[].id` 与字段 `applies_to.kind_ids`，而快照实体上的 `kind_id` 是**公开 id**
（`net:kind:base-spire:Player`）。于是目录与 wire 的引用不闭合：消费者无法用目录校验快照里的 `kind_id`。

- 发现路径：`V-15 成对状态…目录引用闭合` 报 `实体 kind_id 必须在目录声明：net:kind:base-spire:Player`。
- 修复：目录的 entity kind id、`content_types[].kind_ids`、`fields[].applies_to.kind_ids`、
  以及未声明 `entity_ref` 的回退目标集合统一改用**公开 kind id**。
- 加固：`V-15` 逐条校验 kind/field/content/pile/action 的引用闭合，并要求 `pile_ref` 解析到本快照实体
  且其 kind 是已声明的 `pile_type`。

### 2.3 目录 wire 数组按注册顺序输出（net）

身份摘要 `catalog_id` 内部会排序（`WireIdentity.CatalogIdentityInput`），但**wire 数组本身**原来按字典插入顺序
输出，违反 `contract-artifacts §3`（声明按 id 排序、ID 集合排序）。同一目录以不同注册顺序会产出不同字节。

- 修复：`CatalogProjector` 对每张声明表按公开 id 的 UTF-8 字节序排序，并对 `member_kind_ids`/
  `target_kind_ids`/`source_kind_ids`/`required_fields`/`optional_fields`/`category_ids` 等 ID 集合排序。
- 加固：`V-01` 用**反序插入**的同一 profile 产出目录，断言规范字节与摘要逐字相同。
