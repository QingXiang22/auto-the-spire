## 1. 具体反例（上一批就已记录）

`Dominate`（:3425）：先给**目标** 1 层 Vulnerable（升级 2 层），再给自己 Strength，
**层数 = 目标身上 Vulnerable 的层数**（来源 `applyScaledPower { base = 0  perCount = 1
count = { targetPowerAmount { power = Vulnerable } } }`），`keywords = { exhaust }`。

## 2. 表示与**两个**设计决定

| 写法 | 含义 |
| --- | --- |
| `apply_power_self_from_target:<power-id>` | 给自己施加卡牌级 `power`，层数取**所选目标**身上 `<power-id>` 的层数（只支持来源里 `base = 0, perCount = 1` 的子集） |
| `apply_power:<power-id>:<n>`（以及 `_self`/`_all` 两段形式） | 一步之内同时给出**能力 id**与**层数** |

**决定一：做成"步骤"而不是"数值来源"。** 读取时点必须在**它所在的步骤位置**：来源先给目标上易伤，
因此读到的是**施加之后**的层数。若做成"数值来源"，它会在出牌前的 `AmountSourceChain` 里求值——
那时目标还没选、易伤也还没上，语义就错了。

**决定二：能力 id 必须能逐步骤给。** 我第一版只让"层数"逐步骤、能力 id 取卡牌级，于是
`Dominate` 的 `apply_power:1` 被当成卡牌级的能力（Strength）打到了**目标**身上——**检查当场抓到**
（"目标获得 1 层易伤: expected '1', got '0'"）。修正为两段形式后，同一张牌可以给不同收受者上**不同**能力。

## 3. 退出证据

| 判据 | 检查 |
| --- | --- |
| 语法/编译 | 步骤序列 `[target, apply_power:base-spire:vulnerable:1, apply_power_self_from_target:base-spire:vulnerable, exhaust_self]`；来源行 3425；升级先上 2 层；给自己施加的是卡牌级 `power`（Strength） |

| **消耗** | Dominate 打出后进**消耗区**（来源 `keywords = { exhaust }`） |
| 升级形态 | 先上 2 层 → 玩家获得 **2** 层力量 |
| 冻结文本 | 来源行、两形态"先上几层"、给自己那一步的形式、消耗自己逐条一致 |

## 4. 本轮修正的缺陷（我自己的设计错误，被检查抓住）

- **只让层数逐步骤、能力 id 仍取卡牌级** —— 对 `FightMe`（同一能力两个收受者）够用，但对 `Dominate`
  （**不同**能力给不同收受者）不够。表现是"给目标上的其实是 Strength"。
  这不是把检查改宽能解决的，必须把**能力 id 也做成逐步骤**（两段形式），并让 `QualifySteps`
  只限定 id 部分（层数是数字，不参与命名空间限定）。
- 附带说明：`Qualify` 是 `ParseModel` 的局部函数，不能从静态的 `ParseSteps` 调用；
  按既有模式（先在解析期保留原样、再在模型层统一限定）处理，避免把包前缀拼错。
