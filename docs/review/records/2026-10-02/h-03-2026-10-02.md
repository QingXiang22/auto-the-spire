## 1. 做了什么

### 1.1 会话句柄跨进程不复用（真实修复）

原实现用进程内自增计数器生成 `session-N`，因此**宿主每次重启都会重新发出 `session-1`**：旧进程发出的句柄在新
进程里会成功打开**另一局**游戏。这违反 `protocol.md:193` 的「ID 不复用」。

- `ControlHost` 现在带一个**每次构造都不同**的运行令牌（`Guid` 前 12 位十六进制），会话句柄形如
  `session-<runToken>-<n>`。令牌可用构造参数显式指定（测试用 `"tst"` 复现"同一进程"语义）。
- 会话 ID 属于控制元数据，不进入模型特征或重放语义比较（通用引擎设计 §8.1），因此随机令牌不影响可重放性。

**判别力**：修复前两个宿主实例都会给出 `session-1`，检查 `H-03 session_id 跨进程不复用，旧句柄不得指向新局`
会看到 `observe(session-1)` 在新宿主上**成功**而不是 `session_not_found`。

### 1.2 客户端两个真实缺陷（由故障注入暴露并修复）

1. **响应不按 `request_id` 归属**：在超时恢复期间，迟到的原响应会排在 `request_status` 响应之前，而客户端
   只读"下一行"。修复后 `_read_response` 逐行比对 `request_id`，迟到响应归档给它自己的请求，`_recover`
   先取归档再查询。唯一例外是宿主对"解析前就被拒绝的帧"给出的非空占位 `request_id`（`<malformed>`，
   `Net.TheSpire.Host/Program.cs`）：它无法归属到任何请求，只可能属于刚刚写出的那一帧。
   **判别力**：延迟管道注入下，修复前 `start` 会拿到 `request_status` 的包装（只有 `status`/`response`
   两个键），而不是含 `session_id` 的 start 结果。
2. **帧拒绝响应被静默丢弃 → 客户端永久挂起**：超限/畸形帧在解析前被拒绝，宿主只能回占位 `request_id`；
   按 id 归档的严格实现会把它丢掉并一直等到超时（`transport` 组实测挂起）。修复后占位/空 `request_id`
   视为"属于刚刚写出的那一帧"。

### 1.3 客户端启动方式（消除孤儿进程）

`host_command()` 现在**优先直接运行已构建的宿主程序集**（`Net.TheSpire.Host.dll`），不再用
`dotnet run`：后者会再起一层包装进程，"杀掉宿主"实际只杀掉包装，真正的宿主变成孤儿并占住管道——断开注入
的前提是"杀的就是宿主"。回退路径（程序集不存在）仍是 `dotnet run`。

### 1.4 同步后端的状态诚实性（明确的**不做**）

`ControlSession.RequestStatus` **只**回答 `completed` 或 `not_found`。一次 `Step` 在会话锁内走完
pending → settling → 记录结果 → 应答（`protocol.md:193`），因此本地不存在可观察的 `pending` 条目，也不存在
"开始了但无法确认"的情形。协议为异步提供方和进程丢失后的重新识别预留的 `pending`/`outcome_unknown`
**不予伪造**，改由脚本化测试后端单独验证客户端处理。这一点由检查
`H-03 同步后端只报 completed/not_found，不伪造 pending/outcome_unknown` 固定下来。

> 本轮曾实现"关闭时仍有未完成结算 → `outcome_unknown`"，但该分支在同步实现下**不可达**（没有能把条目留在
> settling 的公开路径），属"用死代码冒充覆盖"，已删除。

## 3. 证据类别与边界（不得当成什么）

- **不得**把 `faults` 组的通过读作"真实游戏行为已验证"：延迟管道注入的是传输延迟，脚本化测试后端
  **不结算任何规则**、不代表游戏后端。它们验证的是**客户端与协议状态机**，不是规则或原版一致性。
- **不得**把 `pending` / `outcome_unknown` 的覆盖读作"本后端支持异步"：本后端是同步的，这两个状态在真实
  宿主上不可达（§1.4）。未覆盖：真实异步提供方的**在飞超时**、跨进程账本持久化、并发连接。
- 会话句柄的"不复用"保证的是**同一后端进程的运行令牌不同**；它不承诺跨进程的**账本**继承
  （`protocol.md:199` 明确首版不承诺跨进程崩溃恰好一次）。
