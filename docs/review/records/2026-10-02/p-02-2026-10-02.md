## 1. 测量分界（先讲清楚每个数字量的是什么）

| 段 | 在哪测 | 含什么 | 不含什么 |
| --- | --- | --- | --- |
| 规则推进 | 进程内（C#） | 一次 `step` 的引擎执行（Submit/Answer 到稳定边界） | 投影、序列化、传输 |
| 投影 | 进程内（C#） | `Session.Observe` 生成 `ParticipantView` | 序列化、传输 |
| codec | 进程内（C#） | 规范序列化（`WireCanonical.Text`） | 传输、编码 |
| 编码 | Python | `validate_snapshot` + `tensorize` | 宿主进程、传输 |
| 采样 | Python | 均匀概率 + 按规范语义键采样 | 网络、规则 |
| 轨迹写入 | Python | `build_record` + 落盘（规范字节） | 采样、编码 |
| **wire 每请求** | Python | **规则推进 + 投影 + codec + 传输 + 进程边界** | AI 侧编码/采样/写入 |

**wire 的数字不能与进程内三段相加相比**：它包含管道往返与宿主进程调度。本报告不把两者混着说。

## 2. 可重复负载（四档，按公开候选规模与动作类型分档）

| 档 | 定义 | 本轮实测（进程内，n 为样本数） |
| --- | --- | --- |
| `minimal` | 候选 ≤ 2（暂停期应答等） | n=9，candidates=2 |
| `typical` | 候选 3–5 | n=10，candidates=5 |
| `large` | 候选 ≥ 6 | n=6，candidates=6 |
| `long-settlement` | 只有 EndTurn（一次结算跨完整回合循环） | n=5，candidates=1 |

分档**必须真的不同**（`minimal` 的最大候选数 < `large` 的最小候选数）否则分档没有判别力；
同一受控配置重复运行必须给出**同一分档序列**（`P-02 ... 按候选规模分档，可重复`）。

本轮实测（进程内，单位 ms，`p50/p90/max`）：

```
minimal        advance 0.262/2.533/2.533  project 0.042/0.061/0.061  codec 0.119/0.153/0.153
typical        advance 0.198/0.315/0.315  project 0.039/0.052/0.052  codec 0.125/0.159/0.159
large          advance 0.223/0.341/0.341  project 0.043/0.045/0.045  codec 0.150/0.170/0.170
long-settlement advance 0.411/0.446/0.446 project 0.040/0.045/0.045  codec 0.140/0.148/0.148
```

观察（只报告，不给结论）：`long-settlement` 的规则推进明显重于单张出牌（跨完整回合循环），
投影与 codec 在各档之间基本不变（它们随公开结构规模变化，而不是随动作类型）。

AI 侧与 wire（`p50/p90/max`，ms）：


## 3. 机器/配置/状态与峰值内存

`machine` 组把下列内容写进 `measurement.json`（临时目录，不进源码树）：

- 机器：`platform`、Python 版本、CPU 数、`dotnet --version`；
- 配置：场景 profile、种子、步数上限、执行器 profile、模型身份、字典版本；
- 状态：转移数、各档样本数；
- 延迟：AI 各段与 wire 各操作的 `n/p50/p90/max`；
- **Python 分配峰值**（`tracemalloc`，只覆盖一次真实编码的 Python 侧分配）。

**峰值只声明为 Python 分配峰值**，不是进程 RSS，也不是宿主的托管堆——报告与检查都明确这一点
（`machine/allocation-peak-is-python-only`）。

## 4. 诊断纯度（P-02 的关键纪律）

| 要求 | 证据 |
| --- | --- |
| 诊断不入模型特征 | `diagnostics/*-absent-from-catalog`、`*-absent-from-snapshot`；判别力对照：注入 `diagnostics` 键的快照被编码层**拒绝**（未知键，I-16），而不是被静默忽略 |
| 开启诊断不消费 RNG | `diagnostics/action-sequence-unchanged`、`diagnostics/tensor-digests-unchanged`：同一配置跑两遍，第二遍在每步之间插入额外 `observe`、额外序列化、额外候选查询与二次张量化——动作语义序列与张量摘要逐条一致（若诊断消费了 RNG，游戏流会分叉） |
| 进程内诊断纯读 | `P-02 诊断读取不改变状态/RNG，也不进入公开数据`：`Random.Diagnostics()` / `StateHash()` / 完整观察连续调用后，状态哈希与 RNG 抽取计数不变 |

## 5. 只报告，不写"达标"

- 没有批准的预算，因此本报告**不给任何达标/不达标结论**；检查里也有一条
  `machine/no-budget-verdict` 断言产物中不出现预算类结论文本。
- 本轮数字是**开发机上的单次测量**：没有重复基准、没有线程/精度矩阵、没有跨机器对照，
  因此**不得**作为部署性能结论（那需要第16.2节的明确目标与预算）。
- 未覆盖：宿主进程的托管内存与 GC 行为、多 worker 并发下的 CPU/内存、传输层的帧尺寸分布、
  大候选（≥10）与长局（≥100 步）的极端负载。

## 7. 本轮发现的一处真实性质（值得记录）

**编码层拒绝未知键**：为了给"诊断不进模型特征"造一个能区分的反例，我尝试把 `diagnostics` 字段塞进
快照——结果编码层直接以 `unsupported_structure`（I-16）**拒绝**，而不是忽略它。这比"摘要会变化"更强：
诊断内容连编码入口都进不去。检查据此改为断言"注入即被拒绝"。
