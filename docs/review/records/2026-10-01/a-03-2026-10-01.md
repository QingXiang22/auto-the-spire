## 4. 期望值来源与独立性

- 叠加输入与 `(code, path)` 期望**都是手写**；本套件不调用 `validate.py` 生成期望，也不把实际
  输出回填夹具。
- `(code, path)` 采用**集合等值**：漏报（`缺少`）与虚报（`多出`）都会失败，失败信息里同时给出
  两侧差集与实际集合。反例里"自有检查 + 共享结论对同一事实各报一条"的情况按实际写入期望，
  没有用"只查是否报错"来蒙过去。
- 用例顺序不参与断言（错误收集顺序只用于 `raise_first`，且该用例只有一条期望错误）。

## 5. 本轮修复（改了什么、为什么）

### 5.1 `contracts/layers.py`：L1 结论的路径被写成了"路径+整条说明"

原实现：

```python
for message in assets.schema_errors(document, role):
    findings.append(_finding("I-66", "L1", f"{role}{message[1:]}", message))
```

共享 `jsonschema_min.validate` 返回的是 `"<JSON path>: <说明>"` **单字符串**（如
`"$.status: 'paused' 不在枚举 ['decision','terminal']"`）。原写法只剥掉开头的 `$`，
于是 `Finding.path` 变成 `snapshot.status: 'paused' 不在枚举 […]`——**说明文字被塞进了路径**，
`message` 又重复了整条原文。这直接违反 A-03 的"给错误代码和路径"：调用方拿不到可用于定位的
路径，去重键 `(code, path)` 也随之失真。修法是在 `": "` 处切分：路径取 `$` 开头的部分并把
`$` 换成 role 前缀，其余作为 `message`；切不出指针时整条落在 role 上，不伪造路径。修复后同一
反例给出 `unsupported_structure @ snapshot.status`（`snapshot.entities[0].fields[1]` 等下标路径
同样恢复）。该改动只影响 L1 结论的**呈现**，不改变任何"是否拒绝"的判定；既有 345 项只用
`rule_id`/是否为空，故无回归（实测仍 345/345）。

### 5.2 `encoding/validate.py`：共享层异常从 `validate_snapshot` 逃逸

`_merge_shared` 直接调用共享 `layers.document_findings(...)`。共享 L3 在**已被 L1 拒绝**的
结构上仍会继续索引元素，实测三个反例直接抛异常而不是返回报告：

| 反例输入 | 异常 | 出处 |
| --- | --- | --- |
| `piles[i].known_positions[0].position = "0"` | `TypeError: '<' not supported between instances of 'int' and 'str'` | `tools/contract-check/wire_layers.py:628` → `wire_canonical.card_position_sort_key` |
| `piles[i].known_positions[0] = 3` | `AttributeError: 'int' object has no attribute 'get'` | 同上 |
| `legal_actions[i].fields[0] = 7` | `AttributeError: 'int' object has no attribute 'get'` | `wire_layers.py:777` → `wire_canonical.action_semantic_key` |

这违反 `validate.py` 自己声明的契约（"调用方拿到 `ValidationReport`（收集全部错误）"），
也让 A-04 的张量化前置门在畸形快照上拿到裸异常。根因在 `tools/contract-check/`（本任务禁区，
未改），因此只在**本层**加守卫：捕获共享层异常 → 记一条
`unsupported_structure @ snapshot.shared-findings`（消息点名共享层类型，`related_ids` 含 `I-66`
与异常类型）→ 并在 `checked` 里追加 `shared/L1+L3-aborted-by-shared-exception`，
**不静默、也不假装通过**。判定逻辑未放宽：报告仍非空、路径可见，三个反例各自仍报出本层
原有的结构错误（见 `piles/known-position-wrong-type-still-returns-report`、
`piles/known-position-record-wrong-type-still-returns-report`、
`candidates/field-not-an-object-still-returns-report`）。共享侧的真修在 P-01（见 §6.5）。

### 5.3 判为"夹具自身写错"的两处（改夹具，不改实现）

- `structure/terminal-with-candidates` 最初只把 `status` 改成 `terminal`，实现另外报出
  "terminal 时 `terminal_result` 必须是对象"——实现是对的，改为同时给出合法 `terminal_result`，
  让该例只聚焦"terminal 时候选必须为空"。
- `identity/catalog-binding-mismatch` 最初只改 `catalog_id`。`catalog_digest` 是**内容**摘要
  （不含 `catalog_id`），`assert_catalog` 因此不报错——这与"目录内容身份与字典不一致"的措辞
  一致，判为实现正确；夹具改为**追加一条实体种类声明**（内容身份真的变了）后，命中
  `version_mismatch @ catalog`。

## 6. ④ 未覆盖与残余风险

1. **V-06.4 的上界在合法的 V-06.2/V-06.3 下不可单独触发。** 若位置记录的 `card_ref` ⊆
   `visible_members` 且每牌至多一位，则位置条数 ≤ 成员数 ≤ `total_count`，所以
   `len(positions) > min(total_count, len(members))` 必然伴随重复成员或重复位置。
   `piles/v06-4-positions-do-not-add-cards` 因此同时命中三条（`duplicate_identity`、
   `count_mismatch @ …known_positions`、`invalid_position`），**这是"防御性上界"而非可独立复现的
   违规**；报告在此登记，避免后来者把它当作"已独立验证"。
2. **共享 L3 会把字符串当成员列表遍历。** `visible_members = "card-01"`（L1 已判类型错）时，
   共享 L3 仍迭代该字符串的字符，报出 `dangling_reference @ snapshot.piles[pile-draw].visible_members`
   且消息为 `悬空引用: 'c'`（去重后只剩首字符）。本套件用金丝雀
   `piles/visible-members-wrong-type-canary` 把 8 条结论**逐条冻结**：本层的
   `unsupported_structure @ …visible_members` 是对的，共享那条属于共享层缺陷（P-01）。
3. **同一事实两个码（去重键是 `(code, path)`）。** "每张牌至多一个位置"由本层报
   `duplicate_identity`、由共享 I-29 报 `invalid_position`，路径相同、码不同，两条都保留；
   "重复 field_id" 同理（本层 `duplicate_identity` + 共享 I-88 兜底的 `unsupported_structure`）。
   这是有意的（两个独立判定都可见），但下游若要按码聚合需知道这一点；A-04 不应据此二次去重。
4. **`SHARED_RULE_CODES` 未登记 `I-88`（重复 `field_id`）。** 反例：
   `fields/duplicate-field-id` → 共享结论落到兜底码
   `unsupported_structure @ snapshot.entities[card-01].fields`，而该事实的自然码是
   `duplicate_identity`（本层在同一路径已报该码）。兜底是显式的、没有静默丢弃，故本轮**未**
   单方改映射表；建议 P-01/AI 侧后续登记 `I-88 → duplicate_identity` 并同步
   `SHARED_RULE_CODES` 的说明。组级金丝雀
   `mapping/shared-rule-ids-registered-or-fallback` 会在"未登记却落到非兜底码"时失败。
5. **共享层对 L1 已拒绝结构的健壮性（§5.2）**：本层只做了兜底守卫，真正的修在
   `tools/contract-check/wire_layers.py` / `wire_canonical.py`；在修好之前，任何直接调用共享
   `check_snapshot`（不经本层）的路径仍会抛裸异常。
6. **编码层不做"空适用域"的动作侧判定。** `fixture:owner` 的 `applies_to.action_types` 为空，
   本层视为"无动作域限制"，因此把实体字段塞进 `end_turn` 候选时本层不报
   `field_not_applicable`，只由共享 I-36 报
   `missing_required_field @ snapshot.legal_actions[cand-end].fields[fixture:owner]`
   （金丝雀 `applicability/empty-action-domain-is-not-encoding-layer-fact` 冻结该现状）。
   若 A-04 期望"动作字段白名单"由本层给码，需要先改契约，不能靠放宽共享规则实现。
7. **`members_complete` 类型错误只有共享 L1 报。** `piles/members-complete-wrong-type` 期望
   `unsupported_structure @ snapshot.piles[1].members_complete`（共享 L1 的**下标**路径）；
   本层把非 `true` 一律当"未声明完整"，不额外报类型错。这是有意的：类型归 L1。
8. **A-03 之外的相邻协议约束只经共享层间接覆盖**：`relation.position` 与目录
   `position_schema`（protocol §2 第 81 行）、`Sequence` 的 `min_count/max_count` 与"从 0 起连续"
   （第 96 行）、`Group.multiplicity` 正整数（第 96 行）、终局 `reason_id` 注册与 `outcome` 一致
   （第 64 行）都不在 A-03 原文范围内，本组只在触及时冻结共享结论
   （如 `references/relation-*` 的 `unsupported_structure @ snapshot.relations`、
   `terminal/*` 的 `value_type_mismatch @ snapshot.terminal_result.facts`）。
   这些条目的系统覆盖属于 P-01（共享资产）与 N-01/B-04。
9. **目录侧（L2）约束未在本组新增用例**：`piles` 目录必须含 `net:pile_member` /
   `net:pile_total_count` / `net:pile_members_complete` 三条保留声明、牌堆成员不得在
   `relations/groups/sequences` 重复表达（第 94 行）由共享 L2 与 A-02 的 `manifest` 组覆盖，
   本组只做了"同互斥组作用域成员重复"（I-31）一条。
10. **未做**：性能/容量下的实际内存行为、`validate_snapshot` 的错误**顺序**契约、
    跨样本批量校验（属于 A-04）。

## 7. ⑤ A-04 前置

A-04（tensorize/collate、typed 通道、reference_map/local 索引与 masks）可以直接依赖本层：

1. **前置门**：`require_valid_snapshot(snapshot, manifest, catalog=...)` 已可用作张量化入口，
   失败抛首条 `EncodingError`（码 + 路径）；通过的报告 `ok=True`、`checked` 非空、`skipped`
   明确列出缺目录时未做的检查。A-04 **不应**自己重算字段/引用/牌堆判定。
2. **需要消费的既有产物**：`GymManifest` 的字典/`field_records`/`encode_number`（数值变换与
   容差唯一入口）、`EncodingConfig.capacities`（超限**报错不截断**，A-04 的 padding 上限必须与
   同一份容量对齐，不能各写一套）。
3. **已知需先协商的点**：§6.3 的"同事实两码"、§6.6 的"空适用域不报动作侧码"、§6.7 的
   "`members_complete` 类型归 L1"；若 A-04 的 mask/reference_map 依赖某个码或路径，
   先在本组补一条用例再实现，避免出现第二个判定来源。
4. **必须保留的边界**：容量越限显式 `capacity_exceeded`（见 7 条 `capacity/*` 用例）；
   缺目录时不得把 `skipped` 当通过；`validate.py` 不读隐藏状态、不保存历史、不理解效果 DSL。
5. **建议同步修（不阻塞 A-04）**：§6.4 的 `I-88` 映射登记、§6.5 的共享层健壮性、
   §6.2 的共享 L3 字符串遍历——三条都应回到 P-01/共享资产侧修，AI 侧保持"只报不改协议"。
