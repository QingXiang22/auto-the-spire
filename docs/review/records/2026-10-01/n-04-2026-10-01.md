## 3. 传输契约（逐条对照 `:221`）

| 要求 | 实现与证据 |
| --- | --- |
| UTF-8 NDJSON，一行一帧 | `ReadFrames` 按 `\n` 切**原始字节**；客户端同样按行写/读（二进制 + 显式 UTF-8，避免平台换行翻译破坏分帧） |
| stdout 只写协议 | 除响应行外 stdout 不写任何东西；"host ready" 与所有拒绝诊断都走 **stderr**（`transport` 组验证在被拒绝后仍能继续服务） |
| 帧字节上限显式配置 | `--frame-limit N`（默认 1 MiB）；测试用 `--frame-limit 256` |
| 超限失败、**不解析部分数据** | 超限帧直接产出 `capacity_exceeded`（`retry_mode=stop`），**不**尝试解析已读到的前缀字节；测试同时验证"上限内的帧被正常解析并分发"（判别力对照） |
| 不可解析帧 | 返回 `invalid_input`；**若帧本身是合法 JSON（只是载荷不符 schema），仍保留真实 `request_id`**（宽松解析提取），只有连 `request_id` 都读不到才用非空占位符 `<malformed>`（协议未规定这种帧的 id；见 §5） |

## 4. 走 wire 才暴露的协议契约缺口（已修）

N-03 的检查在**进程内**直接构造 `RequestDto`，绕过了 wire 载荷契约；N-04 走真实 NDJSON 后暴露并补齐：

| 发现 | 处理 |
| --- | --- |
| `start` 必须带 `expected_identity` 与 `scenario_profile`（`:176`），且**不支持就必须在启动前拒绝** | 新增身份校验：与本运行时身份不符 → **`version_mismatch`**（拒绝、不降级、不创建会话）；场景不符 → **`unsupported_capability`** |
| `seed` 是**十进制整数字符串**（不是 JSON 整数） | 客户端按字符串发送；宿主按字符串解析；**并在能力声明 `seed_control=true` 的前提下真正使用它**（此前被忽略——声明与行为不一致） |
| `get_catalog` 的 `catalog_id` **不存在则失败**（`:175`） | 新增校验：不匹配 → **`version_mismatch`** |
| 载荷**不得含未知键**（`:217`） | 由 `RequestDto.FromWire` 强制；宿主把这类失败回给**原 request_id** |

检查侧同步加了 3 条：`start` 身份/场景不符即拒、`get_catalog` 未知 id 即拒（`N-03 start 校验 expected_identity 与 scenario_profile（不符即拒）`）。

## 5. 超时与"不确定结果"（`:197/:199`）

客户端把恢复规则**写进代码**而不是留给调用者记忆：

* 超时 ≠ 未执行：`request(request_id, timeout=T)` 超时后自动调用 `_recover(request_id)`，用**原 request_id** 查询 `request_status`；
* `completed` → 取回**原响应**（不再执行）；`pending` → 抛错并明确"等待或停止控制，不得重发"；
* 其它（含 `not_found`）→ 抛 **`OutcomeUnknown`**，消息写明 **"not_found 不是未执行的证明，不得盲目重发，按 uncertain 处理并停止控制"**；
* 客户端**不提供任何盲目重发 API**（`recovery` 组有一条检查专门断言这一点）。

已知限制：**引擎是同步的**，因此不存在"执行中真的超时"的场景——`recovery` 组只能验证 `not_found` 这条路径（3 条检查）与客户端的规则实现；**真正的在飞超时**需要异步执行或 deadline，与 N-03 报告的 `session_busy` 限制同源，属真实后端/后续任务。

## 6. 未覆盖 / 残余

1. **在飞超时未验证**（见 §5）；`session_busy` 同理不可达。
2. **跨进程持久化未做**：账本保留到会话关闭或进程退出 + 容量上限（`:199`）；宿主进程退出后账本不保留。
3. **帧上限的余量约定**：超限帧被丢弃到下一个换行符（否则无法重新同步）；协议未规定该细节，已在代码注释与本表说明。
4. **`request_status` 的 `outcome_unknown` 状态未被驱动出来**：需要 `uncertain` 会话（异步执行或真实后端故障），当前实现只在同步故障时给 `backend_fault`。
5. 客户端 `send_raw` 是测试用后门（可发畸形帧）；生产路径只经 `request`。
6. 宿主未做**并发连接**支持（单进程单通道），符合本机 stdio 的用途。
