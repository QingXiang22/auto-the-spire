# 术语与表达规范

文档类型：参考（Reference）。供编写项目说明、协作规则、Issue、PR 和进度说明时使用。优先写清具体对象、操作和结果；项目内的简称首次出现时说明含义。

## 使用规则

- 使用读者熟悉且含义准确的工程术语。术语不能代替具体说明，例如写明是哪份测试数据、哪个完成条件或哪条失败记录。
- 下表中的受限说法用于解释旧文档，新增或修改文字时采用推荐表达；数学、游戏规则及外部工具有准确专门含义时按该含义使用。
- 路径、命令、协议字段、类型和 API 名称按原样引用。例如 `fixtures/` 可解释为测试数据目录，实际目录名保持不变。
- 所有说明文档均遵循本规范。修改旧文档时按上下文改写，保留原行为要求、比较范围和失败条件；代码引用与协议样本保持准确。

## 受限说法及具体含义

| 说法 | 在本项目旧材料中的含义 | 推荐表达与限制 |
| --- | --- | --- |
| 夹具／fixture | 测试所需的数据、对象、资源及其准备／清理过程；其中有些文件只是固定输入数据 | JSON、样例输入或固定来源文件写“测试数据”或“固定来源数据”；对象构造器写“测试辅助代码”；数据库、服务等准备工作写“测试环境”。引用工具的 fixture 概念时保留英文并说明具体用途 |
| 台账 | 人工重复记录任务状态、来源核对或检查结论的表格／文档 | 分别写“任务清单”“来源列表”“检查结果”。任务状态使用 GitHub Issues，变更使用 PR／Git，运行结果使用 CI；这些内容的另一份同步副本不进入正式文档 |
| 见证／行为见证 | 某项内容实际运行后产生的可核对结果；有时也被用于指测试程序本身 | 程序写“行为测试”或“测试用例”；运行产物写“执行结果”或“测试报告”。静态声明不能描述成执行结果 |
| 分母 | 计算覆盖情况时必须纳入的来源条目或测试用例总数 | 写“来源条目总数”“必测用例总数”，并说明排除项。实际比例计算可以使用分子／分母，但应先定义统计范围 |
| 对拍 | 给当前实现与另一个实现相同输入，比较双方结果 | 写“差异测试”或“与参考实现比较”；声称独立比较时说明参考来源、输入及比较维度。单侧回放和内部测试分别说明 |
| 收口 | 可能指修复剩余问题、统一接口、完成迁移或完成验收 | 直接写具体动作和完成条件，例如“将加载入口统一为一个”“修复剩余两类错误”。避免只写“已收口” |
| 门槛 | 某项测试、功能或版本必须满足的条件 | 写“测试通过条件”“功能完成条件”“发布条件”，说明适用对象；保留正式工具中的 gate 标识 |
| 结算 | 可能指统计结果、完成验收，也可能指游戏中的效果处理 | 工程进度写“统计测试结果”或“完成验收”；游戏规则中的“伤害结算”“战斗结算”保留 |
| 闭环 | 从入口到结果可连续执行的一段流程 | 写“端到端流程”，并列出起点、关键步骤和终点；局部流程完成的结论应注明实际范围 |
| 切片 | 一次可独立实现和评审的功能范围，有时特指贯穿多层的最小流程 | 写“可独立交付的改动”或“最小可运行流程”，并说明包含哪些层和行为；引用已有名称中的 slice 时保留名称 |
| 冻结 | 固定某次版本、接口、源代码或测试输入，作为后续比较依据 | 根据对象写“版本基线”“接口兼容性约束”或“固定输入数据”，并给出版本／提交；修改限制须说明适用范围 |
| 契约 | 对输入、输出、行为、兼容性和失败方式的明确承诺 | 一般写“接口约定”或“行为要求”；引用正式契约名称及类型时保留原名，并链接具体要求 |
| 证据 | 可能指源码依据、测试结果、CI 记录或发布文件 | 直接写出实际材料和位置，例如“源码依据”“测试结果”“CI 链接”。需要这些材料的任务应说明如何用于判断结果 |
| 身份 | 在规则包和回放中，用于识别版本及配置的一组标识 | 写明实际字段，例如“包版本与摘要”“配置 ID”“随机算法版本”；多个字段共同识别运行配置时应列明，不能只写一个模糊的“身份” |

## 保留的协作与测试术语

| 术语 | 本项目含义 |
| --- | --- |
| 总任务／子任务／执行工单 | 分别组织产品目标、能力成果和可分配给一个执行者的具体改动；均使用 GitHub Issue，层级与状态见 [CONTRIBUTING](../../CONTRIBUTING.md#任务拆分与派发) |
| 测试用例（test case） | 给定前置条件和输入，检查可观察结果的一项测试；代码或命令中的 `case` 保持原样 |
| 测试集（test suite） | 一组有明确范围的测试用例；`suite` 参数及测试集标识保持原样 |
| 持续集成（CI） | 对指定提交执行的自动检查；结果说明该提交在所选检查范围内的表现 |
| 来源目录／公开内容目录（catalog） | 前者记录内容来源和范围，后者是运行接口提供的可查询内容。描述时指明是哪一种；协议中的 `get_catalog` 保持原名 |

## 写作示例

以下仅示范句式，不代表当前交付状态。

- “完成夹具收口” → “将固定来源数据移入 `tools/ci/fixtures/`，并更新读取路径。”
- “见证齐全，分母不变” → “所有已声明内容均有执行结果；必测用例总数保持不变，未支持项仍报告失败。”
- “闭环通过” → “正常开局、地图选点、战斗、领取奖励和返回地图均能通过公开接口执行；独立比较结果另行说明。”

## 自动检查

使用 Vale 3.24.0 执行[项目措辞规则](../../.github/styles/Project/Terms.yml)，运行 `python tools/doc-check/check_terms.py`，安装和完整命令见[文档检查说明](../../tools/doc-check/README.md)。此检查已接入 `python tools/ci/check.py docs` 和文档 CI。

规则覆盖所有 Git 纳管的 Markdown，包括旧说明和 `AGENTS.md`。术语解释页保留这些词的定义及改写示例，因此该页只关闭措辞规则；其他文档没有整页例外。Vale 按 Markdown 结构保留代码、命令、公式和 URL 引用；游戏语义及其他需要上下文判断的表达仍由评审确认。

术语解释维护在本页，可执行的匹配规则维护在上述 Vale 风格文件。新增受限说法时同步修改二者，无需另建审批流程或逐次登记表。
