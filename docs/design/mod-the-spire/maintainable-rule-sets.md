# 编写可维护的规则集

文档类型：操作指南（How-to）。面向规则库作者：把一项机制写成可复用、可验证的规则，并让后续内容作者只需理解其输入和结果。首次接触Engine请先做[规则教程](../../dsl/core/first-rule.md)；base内容作者直接使用[base开发指南](base-development-guide.md)。

## 先确定一次修改属于谁

开始实现前，用一个输入和预期结果描述机制，再选择修改入口。

| 变化 | 主要修改处 | 应保持稳定的边界 |
| --- | --- | --- |
| 组合已有能力、修改参数 | 内容或规则库配置，加行为案例 | 规则包构建器、生命周期、宿主协议 |
| 新增领域效果或查询 | 领域前端、类型化程序、效果/表达式编译器 | Engine执行方式、房间调度、公开注册 |
| 新增权威状态或共享结算过程 | 状态声明、过程和少量绑定，再接领域编译器 | 不在C#回调中维护另一份状态 |
| 改变付款、选择、回合、胜负或永久提交 | 对应动作/生命周期主责 | 叶效果不能代替动作收尾 |
| 扩大可见信息或动作参数 | 规则声明/投影及消费者契约 | 宿主不重算玩法 |

不要把“少改文件”当作唯一目标。前端接受一种写法、领域程序保存它、运行时执行它，是需要一致维护的语义链。要消除的是每张牌都需改生命周期或每个新效果都需改网络注册的依赖。

## 按六步实现一个机制

1. **写可检验契约。** 定义输入、目标域、执行顺序、状态读写、暂停点和结束条件。例如两击3与7应扣血10；攻击后读取格挡应读取攻击完成后的格挡。列明空候选、目标已死、升级和重复执行等实际适用边界。
2. **选择复用单位。** 常量与卡池等差异放配置；重复的运行行为用具名 `procedure`；编译期生成一组声明用 `template`/`use`。原版卡牌使用内容DSL已有原语。只有确实出现相同语义时才提取共享机制，避免预建万能扩展框架。core规则库写法见[0.2作者指南](../../dsl/core/0.2/authoring-guide.md)，base文本过程复用按主清单T07交付范围判断。
3. **让中间表示保存完整含义。** 每个效果持有自己的数值、目标、引用和源位置；条件/重复保存子程序及顺序。显示摘要不能反过来决定执行参数。显式保留兼容适配器，未支持的写法给出带位置的原因，不注册空效果来补数量。
4. **在唯一权威状态上结算。** 持久数据放Engine实体/字段/集合/关系；执行帧局部变量保存本次调用的信息。动态计数在使用处读，X费读取本次已付费用。纯Compute只接收声明输入并返回结果；算法、数值配置、候选顺序和随机消费变化都需要身份与行为证据。
5. **让编排拥有收尾。** 效果可以伤害、抽牌或修改状态；共用出牌过程安排付款、目标选择、hook和结果牌区，外层动作拥有胜负和永久提交。末次击杀仍执行剩余效果和hook；暂停选择必须通过Engine决策续接，不在效果内部另造调度器。长期牌、战斗副本和临时牌各自明确来源与失效点。
6. **交付一个完整机制包。** 同时交语法/领域程序/运行行为/测试用例/作者说明；检查实际加载与身份。随后按阶段扩大公开出口和独立对拍。缺参考或已有无关失败要保留首个差异与范围，不削弱门槛。

## 选择能发现错误的检查

先用独立预期区分容易混淆的行为，再检查集成。不要直接调用待测实现计算期望值。

| 机制 | 有区分力的案例 |
| --- | --- |
| 多效果与顺序 | 3+7=10、3+3=6；修改状态后下一效果读取新值 |
| 重复与随机 | 重复整个块；重复0次；每次随机消费；随机目标不覆盖所选目标 |
| 付款和升级 | X付费后再加能量，后续效果仍读已付X；普通/升级各自效果与hook |
| 生命周期 | 最后一击之后仍治疗、触发hook、进入结果区并提交永久状态 |
| 加载与引用 | 缺引用明确失败；同ID冲突明确处理；声明/解析/加载/行为分列 |
| 观察与宿主 | 隐藏字段不公开；同规则新增公开动作实际可调用；身份变更明确拒绝旧消费者 |

在一个机制验证完成后运行其集成门槛；每次编辑都跑整套地图/训练会拖长反馈并掩盖首个差异。局部工具不替代最终门槛，也不用于宣称原版保真或吞吐提升。

## 给内容作者一个短接口

为机制提供一份能够回答以下问题的作者说明：采用什么写法、参数是什么意思、何时读取状态、是否可能暂停、能放进哪些hook、普通/升级如何不同，以及失败时去哪定位。用一个已运行的例子证明接口，并把详细词表链接到参考文档。

评审时做一次“内容作者修改演练”：只改内容或配置并运行局部案例。如果仍需修改规则包构建器或宿主，先找是否缺少领域接口，或把显示信息误当执行数据。新增状态确实需要绑定时，记录这个边界，不用隐式反射注册来隐藏依赖。

实际base边界与兼容限制见[逐效果设计](effect-ir/plan.md)和[维护成本改良设计](effect-ir/maintainability.md)；在其上新增内容的步骤见[modding指南](modding-guide.md)。

## 把执行历史和实例身份分开

集合中的牌实例描述“有哪些牌”，事件记录描述“发生过几次”。同一张牌本回合打出三次，需要三个完成事件，不能因为集合成员唯一而禁止第二次，也不能为了避冲突让计数只看到第一次。变形是创建替代实例，克隆是复制当前实例字段，长期副本是从长期牌组带入战斗；这三种命令各有来源策略。

为每项状态写明寿命及唯一重置入口。回合标记在回合开始清理，战斗掉血事件数在进入新战斗时清零，长期HP/牌组由Run持有。只有仍在五个牌区的实例才参与全场牌数查询，退场旧实例和出牌事件不参与。base的实现映射见[共享流程说明](control-flow-modules.md)。
