# mod-the-spire 规格

规则依据为[锁定 sts2-sim](../../../reference/README.md) 的源码与顺序执行；本地 `sts2/` 不再裁决当前目标。base 仍以纯 DSL 独立实现，现有旧来源内容逐项迁移并绑定实际来源摘要；不以重新标记版本代替行为核对。

mod 承载游戏规则包及其扩展，core 提供通用引擎。base 使用完整 Engine DSL 定义原版玩法，Spire 是面向内容作者的受限写法。产品范围见[项目规格](../spec.md)，包结构见[base 架构](base-architecture.md)，准确接口见[开发手册](../../areas/base/README.md)。

## 规则包职责

- 用 DSL 声明实体、字段、集合、关系、作用域、动作、选择、事件、流程和终局。
- 原版卡牌、Power、遗物、药水、敌人、角色、房间、地图与 Run 都属于 base；不在 core／Host 中按内容 ID 实现玩法。
- 包只分发 `.spire` 和必要静态 `.json`。来源标识、池成员和源顺序与实际可执行定义分开维护，不删未实现来源来提高完成比例。
- 根入口显式装配，定义、依赖、命名空间和启动顺序确定；未知字段、冲突声明、缺引用、包外文件及执行型 JSON 均明确失败。
- 规则构建后不可变，每局可变状态由同一个 Engine Session 持有。扩展、替换和组合必须显式声明，不能采用最后加载者静默覆盖。

行为要求见[内容行为约定](content-behavior-migration.md)，完整环境验收见[ENV 规格](../environment-completion-and-differential-v1.md)与[实现约束](../environment-implementation-constraints.md)。开发 scope、加载和局部行为通过不代表正常 Run 已恢复。

## 永久状态与战斗副本

| 状态 | 权威归属与写入 | 重建与失效要求 |
| --- | --- | --- |
| 生命／最大生命 | 脱战时属于 Run；战斗时使用明确的玩家副本，在外层结算边界按规定提交 | 下一战读取已提交的永久值，不能覆盖未提交的末杀增长和治疗 |
| 金币、库存、跨房计数 | Run 与其持有实例；通过共享领域操作修改 | 换房保留；战斗临时状态不得重复回写或再次领取 |
| 永久牌组 | 每张牌有独立实例，升级、变换和移除作用于真实来源 | 变换和克隆按各自源规则处理；同定义不同实例不合并 |
| 战斗牌副本 | 保存隐藏的永久来源引用；临时生成牌明确无永久来源 | 临时费用、战斗私有状态和旧牌区在规定边界清理；永久增长仅沿明确字段映射回写 |
| 奖励、访问与提交状态 | 由对应访问拥有，使用稳定的房间／访问标识防止重复提交 | 未解决选择不能提前关闭；跨幕不复用旧幂等键或旧公开句柄 |
| 敌人、Power、能量与战斗历史 | 战斗作用域；按能力定义区分回合、战斗和长期寿命 | 换战重建，清理临时监听和悬空引用；跨战遗物计数单独保留 |

最后一次击杀后，父效果余效、嵌套调用、附着、通知和结果牌区先按源顺序完成，再在外层边界处理胜利、永久提交、奖励及终局。失败与死亡不得伪造胜利奖励；动作重发不能重复支付或提交。

## 共享领域模型

以下是恢复完整环境的目标要求，实际支持范围仍由 manifest、实现及检查结果确定。各领域复用已有 DSL 操作和实例；遇到通用表达缺口时，先提供最小程序和真实消费者，再协调 core。

| 领域 | 权威要求 | 详细行为 |
| --- | --- | --- |
| Run 与访问 | 显式保存阶段、访问标识、父访问及待提交事项；外层余效完成后依源顺序推进 | [Run 阶段与访问续接](run-domain/spec.md#run-阶段与访问续接) |
| 敌人行动 | 每个实例保存当前节点、已选下一招和必要历史，意图读取同一招式事实 | [敌人招式图](enemy-turn/spec.md#共享招式图目标要求) |
| 奖励生成 | 来源上下文控制候选资格、源顺序、稀有度、升级和随机调用；生成与领取分离 | [奖励来源上下文](combat-rewards/spec.md#奖励来源上下文目标要求) |

这些边界借鉴锁定的 [sts2-sim](../../../reference/baselines/sts2-sim.json) 的领域划分，原版源码继续决定规则语义。base 使用 DSL 表达状态与流程，core 提供通用执行能力，Host 只处理控制和公开输出。

## 影响后续规则的历史事实

历史属于玩法状态，调试轨迹不作为规则输入。复用现有 CardPlayRecord、Attack、DamageResult；新增事实须由真实消费者说明需要保存的字段、记录时点、查询范围与清理边界。单个布尔摘要足以表达规则时可继续使用，不为日志完整性记录全部事件。

| 要求 | 状态与顺序 | 验证条件 |
| --- | --- | --- |
| HIST-01 来源与范围 | 保存消费者需要的参与者、回合／阵营、发生序号、出牌执行及来源类别；依规则需要保存发生时的数值，不能事后读取已变化字段代替 | 同一回合的正常回合抽牌与额外抽牌可区分；重复执行、自动出牌及同定义实例独立 |
| HIST-02 记录与续接 | 在对应源事件提交点记录一次；开始、完成、中止分别按源语义处理，暂停回答不重记已经提交的事实 | 选择暂停前后及嵌套执行的次数和顺序符合源码；非法回答不增加记录 |
| HIST-03 寿命与引用 | 事实归回合、战斗或 Run；跨战清理遵守来源要求。源对象移出牌区或销毁后，保留必要值或有效来源关系，不能留下悬空必需引用 | 移除来源后查询仍可按规则运行；新战不读到旧战事实；两局隔离 |
| HIST-04 摘要与公开 | 计数摘要与事实在同一规则路径维护，明确重置时点；公开摘要由授权投影输出，隐藏来源和内部历史不进入 AI 输入 | 规则所需计数正确；改变隐藏历史不泄漏未经授权的信息 |

DeathMarch 的非回合初抽牌计数、Bolas 的上一回合实例关系及 SoulStorm 的当前消耗堆查询分别按 ENV-T06-PR07 验证；当前集合查询不能统一改成历史计数。历史能力随消费者交付，不作为所有正常 Run 工作的统一前置。

## 来源、兼容与验收

行为以锁定的原版源码为依据，参考模拟器用于独立比较。源码恢复缺口、参考偏离和未支持能力分别说明；不通过重录期望或缩小池与用例制造一致。

规则、内容、数值、随机布局或公开结构变化须更新相应产物标识和消费者。静态条目、解析、加载、行为、独立比较及正常公开整局分别验收，不能互相替代。旧 C# 来源只在工具迁移对照中使用，不成为生产依赖或运行回退。

工作分配、优先级和状态只在[GitHub 总任务](https://github.com/QingXiang22/auto-the-spire/issues/28)及关联工单维护；实际结果留在 PR 和 CI。
