# auto-the-spire 当前成果审阅稿

**审阅日期：** 2026-09-29
**审阅范围：** `core-the-spire`、`mod-the-spire/base-spire`，以及它们当前的设计与覆盖文档

## 1. 项目目标与边界

项目目标是为 AI 提供可复现、可观测、可控且可扩展的《杀戮尖塔 2》训练环境。当前约定把工作拆成三个依赖阶段：

1. **`core-the-spire`：** 用 C# 建立通用规则内核、游戏运行态、动作、结算调度、内容注册和 mod 扩展接口。
2. **`base-spire`：** 在内核之上，用共享 DSL 描述原版玩法内容，逐步覆盖单人游戏闭环。
3. **其他 mod 与外部接入：** 组合其他 mod，以实际 mod 验证扩展接口；通过 `net-the-spire` 隔离模拟内核和真实游戏后端。

`base-spire` 是规则内容包，不是内核。原版游戏应当是 `core-the-spire` 加载 `base-spire` 后得到的一种具体规则集。目标范围以源码快照中的单人玩法为准，默认内容全解锁；账号解锁、成就、多人、UI、音频和平台服务不在当前模拟目标内。项目中的 `sts2/` 是本机恢复的源码浏览工程，不是开发者发布的原始源码。

## 2. 当前架构与内容建模方式

运行定义、运行状态和外部观察视图在设计上分开：规则定义描述组合后的内容和配置；`RunState` 保存整局数据，`GameState` 保存战斗数据；观察接口从运行态投影出外部可见信息。随机流由运行会话持有，按需取数并支持固定种子重放；如需中途存档、恢复或分叉，仍需补充随机流游标保存能力。

内容包以稳定、带命名空间的 ID 注册。构建复合规则集时解析引用、组合扩展并生成对外内容视图。卡牌、Power、敌人行为、效果、地图和全局配置逐步转向 DSL/数据定义；C# 内核负责通用解释与调度，避免为每个内容单独增加运行时分支。敌人和 encounter 目前分别主要使用 `.spire` DSL 与 JSON。扩展内容可以注册受控的自定义整局效果处理器。

效果 DSL 已包含攻击、格挡、失血、施加 Power、抽牌、牌堆移动、选牌、重复、条件、计数缩放、事件响应、召唤及部分生命周期操作等原语。效果可以暂停等待玩家选择，并在动作提交后从同一上下文继续结算。牌实例有稳定身份；战斗牌堆移动会保留实例 ID 和升级级别。

## 3. 已实现并有针对性验证的切片

以下是当前代码和测试支持的能力，不代表已经完成全部原版规则。

### 战斗内核

- 玩家、敌人、Power、牌堆、能量、格挡、战斗变量以及效果结算由运行态承载。
- 玩家动作与合法动作观察覆盖若干常见战斗决策，包括打牌、结束回合、选牌和续接暂停的效果。
- 多敌人行动、敌方行为选择、部分战斗阶段和 Power 触发由通用调度逻辑处理。
- 卡牌结算支持嵌套执行上下文、X 费快照、自动打牌、重复效果、伤害修正和部分事件触发。
- 回合末虚无牌消耗、保留牌处理、普通弃牌和敌方行动之间的顺序已有切片测试。
- 随机目标、牌堆随机移动、敌人行为随机选择及遭遇生成有固定种子重放测试；这不等于所有原版随机流和调用顺序都已对齐。

### DSL 与 Ironclad

- Ironclad 源卡池的 87 个成员已有 DSL 声明。其中 85 张进入单人卡池，2 张标记为多人专属，不进入单人游戏卡池。
- 卡池成员使用明确的 `pools` 归属和显式源顺序；有测试检查编译后的顺序和 mod 追加内容。
- Dazed 已作为 DSL 状态牌注册。
- 多组卡牌效果已迁入共享原语，包括动态伤害、选牌、升级、复制、消耗、保留、失血、按牌堆/Power/事件计数，以及由 Power 提供的通用触发效果。
- Well-Laid Plans 的回合末留牌行为已从专用 C# Hook 移入卡牌与 Power DSL，并覆盖基础版、升级版及零张选择。
- Dark Embrace 消耗虚无牌后抽牌的效果顺序有集成回归测试。
- 生成资格元数据已加入卡牌定义；卡池生成规则会据角色卡池过滤不允许战斗生成的牌，并排除 Basic、Ancient、Event 类别。

Ironclad 的**卡池成员名单**有明确的源码对照结果，但这不代表 87 张卡的所有效果、费用修改、升级、Hook 时序和特殊玩法均已达到原版等价。Well-Laid Plans 当前作为通用内容注册，但尚未放入 Silent 卡池，因为 Silent 卡池尚未建立。

### 敌人、遭遇与整局系统

- 项目已有一批以 DSL 描述的敌人及 Power 行为，覆盖攻击、格挡、状态施加、随机/条件行为、召唤、复活和若干战斗事件响应。
- 当前文档列出的 89 个注册敌人是项目已注册清单，不是原版敌人全目录；具体覆盖随迭代变化，仍需要对照完整源码清单逐项审计。
- 核心已有整局地图流转、房间历史、Encounter/Event/Ancient 池抽取、部分事件效果和可续接选牌升级/移除等基础设施。
- `base-spire` 已迁移标准地图生成的一部分配置、遭遇及部分事件/房间内容。遭遇入口和完整原版内容池尚未齐全。

## 5. 尚未完成的目标与主要风险

### 原版内容完整性

- 完整原版敌人目录尚未导入或逐项核对；已注册敌人数量不能作为目录完整性的证据。
- Ironclad 卡池名单虽已对照，所有卡牌的实际效果、升级、变形、附魔、生成来源和源 Hook 顺序仍需逐项核验。
- Silent 等其他角色卡池、完整遗物与药水内容、完整事件与房间、奖励和商店内容尚未完成。
- 当前单局地图、遭遇池、事件池等机制和数据并未完全对齐原版。固定种子可重放不表示与原版随机数算法、随机流划分或抽取调用顺序相同。

### 规则语义与扩展能力

- 全局 Hook 收集和调用顺序、完整伤害/失血钩子、所有卡牌/Power 生命周期组合仍不完整。
- 卡牌运行期修改、牌组变化在战斗内外的完整同步、变形/附魔和特殊资源（例如星星费用）等语义仍有缺口。
- DSL 虽已能覆盖不少案例，但尚未以实际第三方 mod 证明表达能力、命名空间隔离、冲突处理和组合顺序足够。
- 自定义 C# 效果处理器是受控扩展点，但若大量内容必须依赖它，DSL 的可组合性目标会被削弱，需要持续记录新增原语的理由与适用范围。

### 对外接口与真实游戏验证

- `net-the-spire` 的统一动作/观察协议和模拟/真实后端隔离仍是后续工作；当前测试主要直接调用模拟内核。
- 尚未完成面向 AI 的完整回合交互契约验证，也尚未用真实 STS2 后端做系统级差分测试。
- 实际第三方 mod 的端到端加载、规则覆盖和组合测试尚未完成。

因此，当前最准确的成熟度描述是：**通用 C# 内核已有可运行的战斗和整局基础切片，DSL 已迁移大量 Ironclad 与敌人内容，并有较多定向测试；原版单人游戏完整复刻、外部协议和第三方 mod 验证仍未达成。**

## 6. 建议的后续推进顺序

1. **把已有范围盘清楚。** 建立源内容清单，分别列出原版定义、DSL 定义、差异、测试证据和未实现机制；对卡牌池成员、可生成资格和来源顺序保留自动对照检查。
2. **完成一个可验收的战斗切片。** 选定角色、牌组、敌人和 Power，逐步从源实现核对动作、伤害、回合时序、随机数调用和观察视图。优先抽取可供多个内容复用的 DSL 原语，避免用单卡特判掩盖缺失规则。
3. **拓展原版内容覆盖。** 先完成角色卡牌与敌人目录，再按依赖补齐遗物、药水、事件、奖励、商店和完整地图/遭遇池；每批迁移都带源对照和有区分力的行为测试。
4. **明确训练接口。** 定义 `net-the-spire` 的启动、观察、合法动作、提交动作、结果和能力协商，并由模拟后端实现；保持外部 API 只暴露约定视图，不泄漏内部可变对象。
5. **用实际 mod 验证架构。** 选择一个机制多样、源码可审计的 mod，先列所需 Hook/注册能力，再检查其内容能否仅通过 DSL 和已约定扩展点加载；把无法表达的地方反馈为通用规则或接口缺口。

## 7. 供审阅的当前判断

项目选择“C# 通用内核 + 内容 DSL + `base-spire` 原版规则包”是可行的，尤其适合训练环境需要的可观察、可控和可复现特性。主要成本不在 DSL 文件格式，而在 DSL 的语义边界：它必须描述真实内容反复使用的效果和时序，同时限制任意代码扩展对确定性、状态可观测性和性能的破坏。

当前成果已证明若干非平凡内容可以由共享效果语义迁移并测试，但还不足以证明 DSL 对整个原版或第三方 mod 已普遍充分。接下来应以源码清单驱动覆盖率，以行为差分推动通用语义补齐，再用真实 mod 检验扩展接口。具体设计依据与更细的缺口分别见：
