## 2. 语言与规则归属

core 必须配套通用 DSL：作者能声明类型/字段/作用域/集合/关系/过程/动作/事件/观察，并表达查询、条件、有限循环、调用和决策。通用操作及其类型、副作用、边界是 core 的规范；卡牌、伤害、回合、原版随机布局等规则库由 mod 提供。

编译链定为：语法解析 → 带源范围的 AST → 名称/类型/扩展绑定 → 现有类型化 IR → RuleSet。2026-10-04 用户进一步明确：普通规则作者的正式入口是配置式 `.spire` 文件，声明数据与规则行为，不要求作者编写 C# 或编译程序集。C# 构建器保留为底层开发、扩展和检查接口，两者生成同一种执行表示、调用同一个链接检查器与调度器；C# 示例不能替代配置式作者交付。

core/0.1 已采用 ANTLR 4.13.1，正式 grammar 为 [CoreSpire.g4](../../../core-the-spire/Core.TheSpire/Engine/Compilation/CoreSpire.g4)。生成代码纳入源码，正常构建不需要 Java；维护脚本固定工具版本与 SHA256。grammar 无 C#/STS 语义动作。base 0.0.1 仍用现有解析器及公共 AST，属于另一种游戏语言；不能拿它作为 core/0.1 的第二套语法实现。

编辑器能力采用语言服务：语法高亮/折叠可以先做；诊断、补全、悬停、定义跳转共享名称绑定和内容元数据。ANTLR 生成解析树不等于已有 `.spire` 插件。本轮未交付或安装具体 IDE/LSP 插件；后续插件复用正式 grammar 和编译元数据。

完整 DSL 交付必须包括：grammar；语言参考与通用原语目录；语义编译器；最小可运行游戏例子；入门教程；语法错误/名称错误/类型错误的定位；一次端到端 DSL→Session 演示。解析、链接、开局和行为分别报状态，不能只交 grammar 或 C# fixture。

## 3. 随机语义

不增加“集合随机”和“列表随机”两套取样接口。core 的取样按传入候选序列选择索引，保留 Query 的顺序。需要稳定排序的包显式声明 Sort；core 不擅自按内部 InstanceId、公开句柄或展示排序重排候选。

具体游戏的游戏种子解析/派生、随机流布局、候选构造及原版调用顺序由 mod 拥有。通用 PRNG/取样接口由 core 提供；特定兼容实现可由 mod 通过明确版本的后端/profile 注册。不能因原版有特例就在 Session 写游戏名或卡名分支，也不能将随机后端替换成第二个规则调度器。

现在 SamplePickInst 已保留 query 序列；原受控 base 的三个取样点显式 Sort 以保持此前切片结果。RandomService 支持 IRandomProfile / IRandomGenerator 注入，任意长度的流状态快照，核心统一计数；base 提供 VanillaRandomProfile 并通过冻结向量检查。既有内置 profile 兼容保留，不删除或改名伪装迁移。顺序语义更新为 engine/ir@0.2，旧资产身份不可混用。

## 4. 冻结、故障和开发者 API

“冻结”指构建结果固定，不指游戏状态冻结：同一 RuleSet 可共享给多个状态独立的 Session，运行期间规则身份和规则内容不能因作者对象后续修改而改变。作者阶段允许修改；Build 后复制为独立不可变产物，或使作者对象及其子对象统一拒绝再修改。不能只复制 List 外壳而保留可写 Symbol/IR 子对象；`IReadOnlyList` 本身也不保证对象图不可变。当前作者 Symbol/子集合 Build 后统一拒绝修改；IR/Value 的输入集合复制并只读发布，链接表只读，包索引不再写回共享作者对象。包和 RuleSet 共享边界已分别验证，SessionState 仍可变。

Session 是开发者 API，保留公开调用和状态/RNG访问，不新增权限层、只读 facade 或 friend assembly 白名单。开发者直接操作 Session 不会变成新的调度器；正式 Host 与训练环境仍须使用已有统一入口以免配置漂移。

故障处理不要求现在实现动作级回滚或独立日志系统。当前实现是指令级原子性、故障使 Session 停止；文档须准确说明前序成功指令可保留。NoSL 控制协议保持不提供回退。将来出现实际故障需求时再扩展日志切面。

## 5. 现在就降低维护成本的拆分

实施者早拆执行文件，但保留一个 Session、一个执行栈和一个调度器。建议按以下责任分离代码：

| 区域 | 建议落点 | 完成边界 |
| --- | --- | --- |
| 会话驱动 | Session/Scheduler | Start/Submit/Answer/Step、状态与帧栈 |
| 指令执行 | InstructionExecutor 或 Session.Instructions | 指令执行及现有原子单位 |
| 纯求值 | ExpressionEvaluator、QueryEvaluator | 纯计算与查询，不形成另一个调度器 |
| 事件/决策 | EventDispatch、DecisionProtocol | 保持监听器顺序、暂停位置与一次性续接 |
| 作者/编译 | Authoring、Compilation | 可变声明与冻结规则表示分开 |
| 诊断 | Debug | 按需开启的调试模式 |

已按上述职责拆成 Session 的 partial 文件，调用栈与 Drain 仍唯一。后续确有依赖需求时再抽内部协作者；单纯增加类/接口数量不算验收。拆分不改变公开 API、随机消耗、事件顺序、候选、数值和规则身份。不要将拆分与新增 DSL 语义混在一次不可定位的重写中。

## 6. 为对拍增加调试模式

调试模式已实现为 SessionDebugOptions / SessionDebugTrace，默认关闭，不新增通用日志框架。启用后在共享 Session 执行路径上记录有界诊断：外部动作/决策边界、过程/指令来源、事件与监听器执行顺序、随机流消耗、故障位置；稳定边界可另读内部状态，避免每条指令都算全量哈希。

记录采用拉取式只读快照，不在 Session 内调用接收器。记录溢出以 DroppedRecords 表示，FirstFault 即使溢出仍保留。调试开关/输出不改变游戏随机、状态、候选顺序或语义规则身份；调试器不重入 Step/Drain，也不接管游戏规则。tools 在此抽取对拍证据，net 仍输出参与者公开投影。调试轨迹不成为 AI 的额外公开历史输入。

## 7. 本项目里三类边界问题的具体含义

- 可变对象跨阶段共享：原浅冻结缺口本轮已处理。作者对象及子集合拒绝后续写入，IR 输入数组隔离，共享包多次链接不互相修改。
- 重复执行入口：不是发现了 Engine 内第二个解释器；是 Host、BaseBackend、RunCommand 各自规则包构建并 new Session，分别选择切片/正式子集与默认随机配置。解决方式是共享 base 运行时工厂，调试模式挂同一 Session；不禁止开发者自行创建实验会话。
- 靠约定维持的边界：归档前 Legacy 和 Engine 在同一程序集，base 正式/旧注册路径同工程；文档写“正式路径不调用 Legacy”，但编译没有阻断。本次归档已经关闭这部分。本轮已验证 C# SDK 与 core 文本 DSL 共用 IR/链接器/Session，游戏扩展不覆盖核心声明。base 高级声明迁移及具体编辑器插件仍是后续消费者工作，不用首版文本例子冒充完整原版。

## 8. 当前版本及接续边界

core 当前冻结运行时为 engine/ir@0.3（0.2 是前次交付版本）；支持 core/0.1 基础声明和 core/0.2 规则库配置，分别使用 core-dsl/0.1 与 core-dsl/0.2 编译身份；扩展版本也进入包/规则身份。规则身份覆盖语义，源码路径和 debug 配置不改变它。对拍工具现在消费实际 Session 轨迹，但完整参考侧事件/内容比较仍开放。

本轮关闭 CORE-SPLIT/FREEZE/RANDOM/DEBUG 及 CORE-DSL 首版核心编译链。后续由 base 在 ENV 内容任务中实现高级声明扩展、统一正式随机/规则包构建工厂；编辑器插件单列为作者工具扩展，不阻断现有文本规则运行。完整原版、整局、全量对拍、AI 学习效果维持各自验收，不因核心交付关闭。

## 9. 规则库由 DSL 定义，作者以配置组合

用户指出规则库应是 DSL 配置的职责。本轮据此落地 core/0.2 的 imports/template/use，而不是让内容作者通过 C# 构建器逐条拼规则。基础参考仍为 core/0.1，作者入口见 [入门](../../dsl/core/README.md) 与 [规则库指南](../../dsl/core/0.2/authoring-guide.md)，实际例子为 [game.spire](../../examples/core-choice-counter/game.spire) 和 [score-race.spire](../../examples/core-choice-counter/rules/score-race.spire)。

- procedure 复用运行时过程；template 复用类型、初始化、动作、观察等声明组；use 提供一次实例的具名、类型化字面量配置。模板可以组合其他模板，实例声明前缀和库词法绑定防止名称捕获。
- 文件 imports 在加载阶段解析相对路径及依赖顺序，不进入运行时。模板只在编译阶段展开；沿用同一 IR、链接器、冻结和 Session，不创建规则库解释器或每个游戏一套 C# 调度器。
- 包的模板导出元数据只读；默认值及未实例化模板语义也进入规则身份。注释、文件位置不改身份，实际参数或语义变化改变身份。运行时版本未变化；旧 core/0.1 身份保持兼容。
- 规则库作者可以使用现有 DSL 原语表达通用或游戏机制；STS 特化库归 mod/base。已有原语可表达的机制优先放 DSL 库，公共过程抽复用，内容文件提供配置/组合。新原语或确需高级声明前端时才修改 C# 扩展，扩展仍生成共同 IR，不把卡名分支放 grammar/Session。

默认示例直接枚举 Add 的参数为合法操作，省去 Option 实体、尝试计数、重复选择边界和事件样板。保留旧 counter.spire 作为显式进阶例子，不再拿它当普通作者最小入口。此次交付解决作者入口过低与库复用缺口；完整 STS 内容库、整局和对拍继续开放。

当前模板参数限 Int/Bool/String/Fixed/List(Int) 字面量，body 限核心声明和嵌套 use。跨组件引用注入与游戏扩展声明模板化尚未支持；应由真实 base 消费者需求驱动扩展，避免先制造全能语言。多启动过程的既有 LIFO 语义保留，有顺序要求放单个 Setup 中。编辑器插件仍独立验收。关闭证据见 [本批报告](../../review/archived/dsl-rule-library-authoring-2026-10-04.md)。

## 10. 2026-10-05：通用核心边界与独立冻结条件

用户进一步明确：core 是服务多数卡牌游戏及其他规则游戏的底层框架，独立于原版内容。具体玩法由开发者在自己所属的 DSL 规则包中补充。本文修正此前负责人把 core 契约验证与 STS 游戏验收混在一起的建议；不改变完整 ENV 的产品验收要求。

| 核心提供的机制 | 游戏包决定的规则 |
| --- | --- |
| 类型、字段、实例、集合、关系与作用域 | 哪些对象是卡牌/角色，哪些集合是牌区，哪些字段是资源 |
| 调用、条件、循环、事件派发和确定执行顺序 | 回合阶段、伤害修正、死亡处理、效果的先后与适用条件 |
| 选择暂停/续接、候选与回答校验 | 何时选牌、选哪些牌、选完怎样结算 |
| 随机接口、流状态、版本与消耗记录 | 游戏种子/流布局、候选构造和游戏特定随机算法 |
| 观察权限与知识事实表达 | 什么可见、何时揭示、哪些已知身份/位置失效 |
| 明确的 terminal/fault 指令语义 | 什么时候判定胜负，以及终局之前还有哪些程序需要执行 |

例如“最后击杀后仍需完成哪些效果”由游戏 DSL 包决定。core 只保证顺序执行、调用/事件/暂停和 terminal 的已声明行为，不内置死亡余效、自动完成整轮结算或 STS 专用阶段。当前 terminal 立即停止；包需要的前序处理应在发出 terminal 之前完成。未来需要修改通用调度契约时，必须给出与游戏概念无关的能力定义与版本迁移，不能把游戏策略直接放入 Session。

核心冻结按已承诺的通用能力独立验收：语法/类型/引用与依赖绑定；初始化/事件/暂停续接/终局/故障的明确语义；状态生命周期与集合归属；确定性、数值、随机、公开权限；规则身份、不可变性与兼容策略。不能把全原版内容、完整 Run、参考侧支持度、游戏最终效果或训练效果作为 core 冻结的前置条件。游戏消费者可以提供发现缺口的案例；核心接受的变更仍须被还原成通用原语或语言组合问题。

本节审查时点的两项通用契约问题为 Start 顺序不一致及枚举域未绑定。随后已按用户授权修复并完成第11节冻结交付；具体行为及旧版本迁移以冻结契约为准。

DSL 模板连接共享类型/状态/程序是否需要扩展，按通用组合能力评估；不以“尚未有抽牌/伤害模板”判断核心未完成。现有集合按定义保存、Scope 不自动复制集合，可以成为明确契约；若开发者确需实例化容器能力再提出通用需求，不先重写存储。未承诺的高级模板参数、完整游戏库、Lua 与编辑器不自动成为当前核心冻结门槛。

freeze 的含义是将明确范围的接口与语义作为版本基线维护，允许修复和兼容扩展，破坏性变化另行版本迁移；不意味着禁止新增通用能力。完整环境及其对拍继续由 base/tools/net 的 ENV 项承担。当前事项只维护于 [唯一清单](../../review/tofix/README.md)。

## 12. 2026-10-07：call与scope求值块占位

本节记录用户自顶向下审阅core DSL时确定的拟实现行为；当前core/0.1、core/0.2及engine/ir@0.3没有实施这些新写法，不作为已支持语言参考。

`call` 引用独立文件中预先定义的具名代码块，引用写成 `命名空间:代码块名`，编译时绑定。代码块没有返回值，正常执行完毕后继续调用者。可以显式指定当前操作对象，省略scope时继承调用位置的当前 `this`；具名输入另按第14节的载荷约定传入。这里的scope表示当前操作对象，与现有 `ScopeId` 的实体生命周期容器分开。

用户提出的字段形式为：

```text
call = {
    scope = player
    block = rules:PrepareOpening
}
```

`player` 等具名对象从调用位置的上下文取得，其含义由相应游戏规则入口提供。此前提出的 `player => { block = … }` 保留为语法候选，本节没有决定两种拼写同时发布。

用户决定暂时保留 `scope = { … }` 的外形，内部求值语言留待后续扩展：

```text
call = {
    scope = {}
    block = rules:PrepareOpening
}

call = {
    scope = { futureSelector = { anyFutureContent = true } }
    block = rules:PrepareOpening
}
```

- 解析时识别scope块边界，保留内部原文和源码位置。正常闭合的块，无论是否为空、内部怎样书写，当前都不解释其内部语法，不绑定内部名称、不检查内部类型，也不执行内部内容。
- 编译时将两种块统一降为“读取调用位置的当前 `this`”；运行时取得该对象，而不是编译时固定一个对象。即使块内写了其他对象、调用或未来语法，其当前行为仍是使用 `this`。
- 占位规则只作用于scope求值块的内部，外层call的代码块引用仍须正常绑定并执行。块边界仍须能被识别，保留正常的外层语法检查。
- 编译诊断应提示“scope求值块尚未实现，内部内容已忽略，本次调用使用当前this”，包含源码位置；空块同样提示。warning属于编译期输出，不在每次运行调用时重复发布。诊断的排期及状态唯一看[当前清单](../../review/tofix/README.md#当前任务)。

这项决定保留未来扩展位置，没有定义内部选择表达式、返回语句或新执行后端。后续启用真实scope求值时须显式处理占位行为到实际求值行为的版本迁移。

## 13. 2026-10-07：实体只持有属性，行为由独立块执行

用户明确本轮DSL设计原则：实体只持有属性，不持有方法。内容定义描述属性结构；行为定义为独立文件中的具名代码块，执行规则通过第12节的 `call` 引用它们。属性仍可被执行规则读取和改写，这项原则不要求实体不可变。

`scope` 指定代码块执行时的当前对象，省略时继承调用位置的当前对象；它不把代码块变成该对象的成员方法。`block` 仍是编译时绑定的具名块引用，没有返回值，不通过实体查找或派发同名方法。

[STS2入口草案](../../examples/core-syntax-review/sts2-rules.spire)据此撤除内容定义中的 `blocks` 分区，不将 `play`、`use`、`onSpawn`、`reset` 声明为实体方法。它们的行为与执行时机由外部规则块承担；具体内容如何关联到效果块、执行入口如何声明上下文约定尚待审阅，不在本原则中提前确定新语法。此处是设计决定，未改变冻结实现。

## 14. 2026-10-07：初期采用具名对象与具名输入

用户决定初期采用具名对象和具名输入，以减少作者的心智负担；Clausewitz脚本的上下文链与宏式参数替换留作后期重构参考，本轮不为它们增加语法或预留实现。

具名对象是执行入口提供的实体引用，例如出牌者、所打卡牌、选中目标。具名块像 `event` 一样声明所需载荷的字段名与类型，调用处按名字提供数值、属性值或实体引用；编译器据声明检查输入。属性值是传入时求值的值，实体引用指向块可读取、改写的运行时对象。

以下为独立块文件的语法候选；领域类型由游戏规则包定义，本例仅描述Player作为目标的场景：

```text
namespace sts2.cards;

block ResolvePlay {
    payload = {
        actor = Ref(Player)
        card = Ref(Card)
        target = Ref(Player)
    }
    body = {
        // 使用传入的具名输入执行规则。
    }
}
```

调用处显式提供本次输入：

```text
call = {
    block = sts2.cards:ResolvePlay
    payload = {
        actor = playerA
        card = playedCard
        target = playerB
    }
}
```

`scope`只决定当前 `this`，切换它不改变载荷中actor/card/target的角色关系。块仍静态绑定、没有返回值，实体仍不持有方法。具名输入机制已选定，`block`/`body`及块内访问输入的具体拼写、载荷省略/转发和可选字段规则尚待定稿；本例全部显式传入，不把这些候选写法宣称为现有编译器能力。具体卡牌到效果块的关联方式继续按第13节留待审阅。
