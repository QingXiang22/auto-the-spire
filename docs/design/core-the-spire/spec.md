# core-the-spire 规格

core 是通用桌游规则引擎；STS2 是首个游戏包。产品范围见[项目规格](../spec.md)，具体执行行为见[核心接口与兼容要求](../../contracts/core-engine-baseline.md)。文档只维护当前要求，历史实现及检查数量由 Git 和 CI 保存。

## 目标架构：通用桌游运行时

- 提供类型化状态、集合与关系、作用域、查询、动作验证、原生决策暂停与续接、过程、事件、随机和观察。
- DSL 与 C# 构建 API 降为同一 IR，由唯一 Session 执行器推进。游戏效果、生命周期和 Run 由游戏包的 DSL 定义；core 不按游戏内容 ID 执行效果。
- 规则定义构建后不可变，可被多局共享。实例状态属于各自 Session，执行帧保存调用局部值、循环游标和暂停进度。
- 纯过程沿调用图校验；只读查询与投影不写状态或消耗随机。候选、指令、调用和事件超预算时显式失败。
- 包、编译器、执行语义、内容与随机配置采用明确标识。语义变化须更新兼容检查，不能用旧产物标识加载新规则。
- 外部计算后端只属于后续扩展设计；base 当前仅使用 DSL 与静态 JSON，不因这项设计引入 C#／Lua 玩法回退。

## 游戏建模与支持判定

将一个确定版本、模式与内容范围的游戏描述为：

\[
G=(P,S,I,M,L,T,O,F)
\]

| 要素 | 含义 | 规则包需要说明的内容 |
| --- | --- | --- |
| \(P\) | 参与者集合 | 谁可以作决定；参与者标识与其控制的实体分开 |
| \(S\) | 完整逻辑状态 | 实体属性、集合与关系，以及阶段、待结算事项和影响后续规则的历史事实 |
| \(I\) | 初始化规则 | 从配置建立初始状态；随机开局可以产生初始状态的概率分布 |
| \(M(s)\) | 当前需要作选择的参与者 | 无人时自动推进；一人时顺序选择；多人时表示联合选择，不能擅自改成公开的依次选择 |
| \(L(s,p)\) | 参与者的合法选择 | 可执行的动作、参数、目标、响应与放弃；联合选择还须满足游戏规定的联合约束 |
| \(T(s,\mathbf a)\) | 状态转移 | 执行本次选择和相应结算；随机转移写为 \(s'\sim T(s,\mathbf a)\)，确定转移只有一个后继 |
| \(O(s,p)\) | 给参与者的观察 | 公开信息、本人私有信息和规则授权的已知信息；不等于完整状态 |
| \(F(s)\) | 终局与结果 | 是否结束，以及各参与者的胜负、得分或游戏规定的其他结果 |

这里的“状态”包含继续运行所需的信息。例如等待别人响应时，原牌的目标、响应窗口、已经完成的部分和接下来应执行的位置都必须被保存。若历史会影响规则，应在状态中保留相应事实；玩家作决定时可使用其观察与行动历史，不能假定当前一张观察快照包含其全部已知信息。这个划分参考 [OpenSpiel 的 Game、State、合法动作、联合动作与随机节点概念](https://openspiel.readthedocs.io/en/latest/concepts.html)，是本项目的建模约定，不要求采用其 API 或数据结构。

实体只持有属性，行为由独立规则程序执行，见 [实体与行为分离原则](core-architecture-decisions.md#内容自有规则与公共操作)。牌区、阶段、伤害、死亡、技能与胜负是游戏包的定义；模型不要求内核拥有这些专用类型。作用于实体的程序可以修改其属性，实体本身不因此拥有方法。

### 如何判断内核具有建模能力

能力审查判断模型中的状态、选择、结算和信息规则能否由现有内核原语组合表达。映射路径为 **游戏模型 → 游戏包声明与规则程序 → 通用 IR → Session 执行**；模型中的每类规则都应有可说明的落点。只有抽象模型而没有这条映射，仍不足以说明内核具有相应能力；能够说明映射后，不必再交付该游戏的全部内容来证明 ability。

具体游戏的交付另有内容覆盖、实际加载、行为与差异测试验收。本项目当前承担这项交付的是STS2；其他游戏包不作为当前验收的额外实现任务。这个边界与 [通用核心独立固定条件](core-architecture-decisions.md#通用内核与游戏规则分离)及 [ENV实现约束](../environment-implementation-constraints.md#1-决策边界与执行范围)一致。

设 \(c\) 是内核的完整执行配置，\(\alpha(c)=s\) 是它对应的游戏状态。\(c\) 包括持久状态、程序栈与局部槽、事件/循环游标、待决策请求、随机状态和会话状态；不能仅把 `Session.State` 当作它。支持判定以宿主可交互的边界比较，允许多个内部指令实现一次逻辑转移，但分解不得额外公开信息或改变可作出的选择。

表达能力审查检查以下对应关系，实际游戏包实现时再验证其具体行为：

1. **初始状态与状态表示。** \(I,S\) 可由初始化程序、实体字段、集合与关系表示，包括影响后续规则的历史事实。
2. **轮到谁与合法选择。** \(M,L\) 可由参与者绑定、条件/候选查询与决策程序表达。动作查询与提交校验的一致性属于内核接口维护。
3. **结算与概率。** \(T\) 可由状态命令、分支、调用、循环、事件、暂停续接与随机原语组合表达；游戏规定的处理顺序由规则程序组织。
4. **信息。** \(O\) 可由字段/区域可见性、观看者授权事实与宿主交互路由表达。
5. **终局。** \(F\) 可由规则程序判定并发出类型化终局结果，结束时机由游戏包定义。

适用范围是可离散表达、规则可计算、单次推进可在配置资源预算内完成的游戏。状态容量、数值范围、候选组合数、调用/事件深度属于具体实现边界；是否需要扩展由实际消费者暴露的通用组合缺口决定。当前顺序决策可表达多玩家依次响应；同时选择是独立的协议能力，不能由顺序响应推断。

## 当前入口与扩展边界

语言参考按能力分层维护：[core/0.3](../../dsl/core/0.3/language-reference.md)、[core/0.3](../../dsl/core/0.3/authoring-guide.md)及[core/0.3](../../dsl/core/0.3/authoring-reference.md)。低版本参考仍服务受支持语法，不能仅因版本号较低删除。

开发者从[规则教程](../../dsl/core/first-rule.md)、[宿主教程](first-host.md)和[Session API](session-api-reference.md)接入；持久状态与执行帧区别见[运行态模型](runtime-state-model.md)。

当前执行约定按顺序处理决策，同时选择等能力须由实际消费者提出并单独验证。原版内容覆盖、正常 Run、多人玩法及独立参考比较各有自己的验收条件，不能从通用编译或计分示例成功推断完成。

修改核心能力前提供最小通用程序，说明现有表达缺口、预期行为和受影响消费者。状态、原子性、暂停续接、数值、随机与可见性继续遵守核心约定；重要选择维护在[架构决定](core-architecture-decisions.md)，任务与运行结果使用 Issue／PR／CI。
