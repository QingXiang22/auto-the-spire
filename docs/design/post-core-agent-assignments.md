# 项目任务、文档管理与模块分工

校准：2026-10-20。总入口是[docs/README](../README.md)，当前事实只维护[任务清单](../review/tofix/README.md)。本文规定优先级、交付责任和协作流程；第3～6节保存各线完整验收合同，[角色提示词](agent-goals.md)只提供接单方法。

## 0. 任务与文档管理规则

2026-10-19工作流维护：当前入口只留最近生产批和正在进行的负责人维护，旧批次通过records索引查证；纯参数配置成组交付，新增机制才扩契约及边界判别。遗物调试按名称筛选，完整覆盖报告统一由批次CI生成；具体批次／重跑／集成规则只维护在[检查节奏](../review/tofix/README.md#每批集成与重排条件)。

采用“领域分类→可验收工作包→必要实现步骤”的执行结构，整局里程碑另作集成验收。领域回答有哪些工作，工作包说明本次交付什么、唯一主责、依赖、完成条件及证据；实现步骤只放对应技术工作包，避免把每张牌／每个文件变成项目级任务。现有ENV编号保留为合同和证据索引。

### 0.1 优先级及排队规则

| 优先级 | 判定 | 本项目如何执行 |
| --- | --- | --- |
| P0 | 工作区/数据破坏或导致现有协作无法继续的紧急事故 | 负责人明确登记后中断当前包处理；不把普通unsupported都提P0 |
| P1 | 当前推进阶段的关键路径、可信度缺口或必需出口；具体主线见主清单 | 由主清单当前交付和领域顺序安排，保留真实依赖；旧P1标签不自动覆盖新交付范围 |
| P2 | 下一阶段的必需能力；目前为完整Ironclad M02 | 仅纳入当前交付明确需要的部分；不要求先完成整个共享机制族或清全部长尾 |
| P3 | 五角色/进阶/全量候选及不阻断当前目标的维护 | 保留完整范围，按后续阶段推进；随改随修注释债无需另占整线 |
| P4 | 需候选稳定、用户指定或独立需求才能启动的工作 | 明确触发条件，当前不认领；真实客户端、指定mod及作者工具等单列 |

P值是项目排期，严重程度是缺陷影响；二者不能互相替代。历史报告里的P1/P2缺陷等级按原语境读，不自动决定新任务先后。任务ID如ENV-T01不含优先级，重排不改ID。负责人负责优先级/范围/阶段关闭；执行者发现影响变化时给出具体受阻路径，负责人只提升必要依赖，不把整族所有内容都升为P1。这里的P定义为本项目决策，没有复制其他团队的修复期限或承诺工期。阶段切换时负责人重排已就绪任务，把新阶段关键路径提升P1；不修改稳定ID，不将未来阶段永久固定成低优先级。

### 0.2 状态、认领与在制品限制

2026-10-17按用户最新要求，工程分配以可运行的整局交付为单位：首幕连续闭环、跨幕生命周期、完整Ironclad胜负。下文“一个完整机制包”在实施时服务于这条交付主线；Feed/药水/随机等细项用于依赖追溯和验收，实际阻塞才拆解，不以新增用例数量或单项测试通过替代产品进展。每线仍只推进一条已认领主线，明确文件边界，并在集成窗口统一验收。

同日用户进一步指出问号房可解耦，不应被固定seed的首个失败点牵引而在事件、敌人和协议之间反复切换。事件按共享能力及完整选项成组交付，直接验证生产目录／领域操作，再在集成窗口接回正常Run；仅在真正缺共享能力时展开依赖。受控事件、正常可达、公开可用与独立对拍仍分层记证，模块独立验证不代替整局完成条件。

同日最新规划要求进一步按卡牌、附魔、怪物、共享机制、事件、地图、商店、营火、先古之民、遗物／药水、奖励／宝箱和角色／进阶分类，公开／对拍／发布另列配套工作。领域总览与当前顺序只维护[主清单](../review/tofix/README.md#当前任务)。旧任务P值及接手建议保留为追溯，遇冲突按主清单新顺序；既有暂停项、文件主责和完整验收合同不变。一个事项只选一个主要归属，其他域标依赖，不用分类重排宣称实现完成。

执行约定：领域目录维护长期范围，[当前交付](../review/tofix/README.md#当前交付)唯一登记完整内容组的目标、状态、主责、范围、依赖与证据。按用户最新测试取舍，整组实现后本地默认只跑受影响单元测试和少量固定种子对拍；广覆盖回归交给 push／PR 的 CI，正常整局／矩阵／性能留到对应里程碑，详见[检查节奏](../review/tofix/README.md#每批集成与重排条件)。这替代此前“每小批立即全量集成／正常公开取证”的安排；原最终验收条件保留。Neow先于正常首幕验收，开发开局首幕只是中间检查。

待认领→进行中→待验证→已验收；暂缓写触发条件，阻塞写依赖ID、最小复现、受阻case及仍可继续的任务。生产实现完成但双侧证据缺失，标待验证/对应比较阻塞，不能伪装已验收，也不能因此停止其他独立生产任务。

每条执行线最多一个可验收交付进行中，一个交付一个主责；必要共享能力和内容消费者属于同一批的依赖，不按文件拆成独立进度。A/B/C在主清单当前交付中登记实际会话／目录／下一成果；旧ID详情链接该记录，历史会话注明证据与结束边界，目录责任不等于认领。文档校准不表示认领生产编码；已实施的迁移与未实现残项分别核对，不能把旧review阶段当当前状态。

每包进入进行中前已有：目标/非目标、源或接口依据、依赖/修改范围、可区分的完成条件。包过大时按用户可操作的行为或完整机制族拆子项，不按“读源码/写前端/写测试”拆成互不交付的项目目标。代码/本地检查完成交待验证；需要的加载、行为、对拍和公开证据齐备后，负责人验收该包。父项还须满足原ENV合同，子包全绿不自动关闭父项。

### 0.4 交接与变更格式

每份交接围绕一个任务 ID 或机制族。先用一句话说明交付的用途，给主清单与工作包的具体入口，再说明接手第一步、前置条件、预期结果及原完成条件。没有待续工作时明确本次维护完成，不创造后续派单。详细证据依次说明：

1. 实际新增能力、修改目录及关键语义/接口变化。
2. 构建/内容/Profile/seed 与源依据。
3. 执行命令、返回码及双侧/公开证据。
4. 首个差异、未验证范围及下一已就绪任务。

执行者将长日志保存到 artifacts，在当前任务详情附证据链接和明确状态。已交付能力、实际验证与未验证分别写明；负责人复核、执行者自报与源码推断不能混用。交付前按[接手自查](../AGENTS.md#写成可以接手的交接)确认六项信息可定位，不依赖历史聊天。

负责人保留被替代决定的日期证据，并将当前有效决定回写主清单或实现包；在多份旧报告顶部追加文字不能替代这一更新。旧问题后来有修复自报时，工作包保留方法与判断条件，当前剩余项指向主清单；不要继续把旧复核缺陷写成当前实现事实。

优先级/范围/身份/core/参考裁决变化由负责人写明原因及受影响ID；实现者按完整冻结契约接续。更新导航或移动文档时修复入链/相对链接并运行doc-check及git diff --check；纯文档不重跑规则套件。共享workspace禁止reset/清理/自行提交，用户授权的文档整理按路径校验与原文备份执行。

### 0.5 参考依据与本项目取舍

- [Microsoft团队规模化规划](https://learn.microsoft.com/en-us/devops/plan/scaling-agile)：采用层级目标及可交付小项；本项目用阶段/工作包命名，不强行引入完整敏捷仪式。
- [GitLab Issue Triage](https://handbook.gitlab.com/handbook/product-development/how-we-work/issue-triage/)：区分优先级与严重程度，按产品方向/影响/容量排期；本项目P0～P4由负责人按当前关键路径定义。
- [GitLab DRI](https://handbook.gitlab.com/teamops/equal-contributions/)：每个任务有唯一主责/决策归属，协作方不稀释责任；本项目不增加额外管理层级。
- [GitLab文档信息架构](https://handbook.gitlab.com/handbook/about/handbook-usage/)：相同事实保留一个维护位置，其余交叉链接；本项目总入口/清单/实现包/证据各管一件事。

本项目具体P级、阶段、在制品限制和目录归属是负责人结合当前代码与用户目标作出的安排，以上团队实践仅提供组织方法。

## 2. 三条线共用的接口与协作约束

1. **现有工作区接续。** 旧92ccd34／engine/ir@0.3只作历史锚点；活动版本与语言见[核心契约](../contracts/core-engine-baseline.md)及实际工程／manifest。禁止检出旧标签覆盖工作区；不得按历史版本假定当前能力。
2. **A拥有玩法包。** A在DSL中定义状态、规则与初始化；B/C通过Engine通用加载同一manifest创建独立Session，Start一次。包身份、scope、角色／进阶及实际字符串seed必须可核对。RunConfiguration／BaseSpireRuntimeFactory是冻结C#对照API，不是当前跨线依赖；未恢复的正常范围继续拒绝。
3. **权威状态/规则归属。** Engine类型化存储为权威，回合/伤害/死亡/地图/奖励在base包；不另造调度器、第二RunState或参考答案。复用core/0.3文本库、类型化分派及领域DSL规则；不恢复旧C#领域lowering作为生产后端。
4. **跨线和公开边界。** 同构建/config/seed/Profile；候选来自Engine稳定边界，隐藏状态只作诊断；参考独立执行。跨模块需求给接口/版本/复现后由文件主责修改；stub不得作生产验收入口。
5. **整组完成后轻量验证。** 用户最新指令优先于原逐批全量门槛：本地默认受影响单元测试＋少量固定种子对拍，广覆盖回归交给 CI；整局／矩阵／性能按阶段验收。CI 失败后定向修复，本地只复跑相关部分。B协调共享obj/bin，构建与执行同一产物串行，不逐文件或逐怪启动行为套件，不刷seed找通过。
6. **冻结core默认不编辑。** 通用缺口给最小语法/SDK复现、预期/实际/受阻case交负责人，继续不受影响任务；不忽略余效、改变随机或另建运行时绕过。


## 3. A：BASE-01/02/03，正式规则包与完整原版

### BASE-01：正式入口与真实开局

交付由同一DSL包定义的正常角色开局和通用加载接入，复用DSL内容、静态来源catalog、原版seed／流布局与随机Profile；启动前完成配置，启动一次。`base-spire-singleplayer-dev-v1`是待恢复的验收身份，当前不能请求成功；以manifest明列的scope为准。原型 `.author`、每卡一张的诊断牌组和固定 Cultist 遭遇不得成为正式开局。未支持内容不能静默丢弃或回退 Legacy。

首先把真实起始牌组/遗物/资源、首次洗牌/抽牌、至少一场真实遭遇、战斗奖励与地图后继接通到同一入口；抽出一个实际复用的 DSL 共享机制验证普通/升级及适用分支。与 B 交付 `formal-start-source`、`rng-initial-shuffle`；与 C 交付正常 `describe→catalog→start→step→observe` 公开路径。交接必须包含实际开局命令、配置/seed、已支持范围和轨迹，不仅包含内部检查输出。此项只是完整 Run 的起点。

### BASE-02：完整 Ironclad，近期阶段里程碑

沿真实 Run 阻塞顺序实现完整战斗、生命周期/事件、长期状态与所有房间流程：地图/遭遇池、奖励/选牌、商店、营火、宝箱、古代人、事件内战斗及返回、幕转换、最终事件到真实胜负。长期牌与战斗副本须保留来源；Feed 最大生命等适用永久变化只写回正确实例，最后击杀不能提前截掉父效果、监听器、奖励或结算。

先补首批必测中的重洗、头槌中途选牌、敌人死亡/Power 时序、Feed 跨房间、同定义不同实例永久变化、最后击杀余效、事件战斗返回、奖励幂等；这些是实际功能的验收点，不是另起纯测试任务。每族内容同批加入 B 的参数化两侧 case，C 同批发布所需观察/候选。

BASE-02 完成申请须同时具备：正常 Ironclad 开局；固定进阶 0 的 `ENV-IRONCLAD-00`～`07` 全部严格执行；另有冻结的完整四幕胜利和真实死亡脚本；必需房间/非平凡长期状态定向比较；同正式构建的公开 Host 完整胜负轨迹。人工改血、无敌、固定三房间、全部 seed 早死、超时截断均不能替代上述交付。完整 Ironclad 通过后才能使用 `base-spire-ironclad-singleplayer-v1` 并申请阶段关闭，不能宣布五角色环境完成。

### BASE-03：五角色与完整可达内容

在共享规则和 Ironclad 路径稳定后补 Silent、Regent、Necrobinder、Defect、各角色资源及全部单人可达内容/进阶。B 提供源分母和遗漏列表，A 按机制族/正常 Run 阻塞处理；需要并行内容作者时由用户明确目录分工，共享运行时仍由 A 维护。声明、加载、行为、对拍、公开可用五种证据分列，不能把在快照中出现当成效果已验证。

全范围才使用 `base-spire-singleplayer-v1`。缺来源的必要内容仍计未完成，参考缺内容不缩减本项目分母。每角色都需正常多幕胜利/死亡证据；协同完成 120 对矩阵和 ENV-06 候选，负责人决定原版冻结及 AI 下一阶段。

## 4. B：DIFF-01/02，日常严格对拍

### DIFF-01：现有比较器成为严格测试入口

活动入口为`tools/differential/`，当前仅保留原suite及显式未支持语义；旧Comparator／FixtureSuite／适配器只在迁移对照。先恢复一个原case的DSL会话与独立参考执行，再按源依赖扩组。完整regression仍为17个原ID，缺失项保持unsupported；历史“七个通过／五个未支持”不再作为当前分母或派单，不删ID、不换弱case，也不重启旧C#环境伪装DSL比较。

版本化 suite 预先登记必测 ID、范围、配置/seed、语义动作、必需比较维度和预期终点；缺 case/记录、零执行、参考不可用、unsupported、异常、超时、首个差异、错误终点或缺维度均非零。`compare` 的旧宽松返回码不得当验收成功。受控初始化只用于标明的机制 case；正常 Run 禁止运行中改字段/强制清场。

接 A 工厂后的 base 侧必须与 Host 使用同一正式配置，参考侧独立执行同一语义选择。实例对应按初始/生成来源稳定建立，不能按结果重新匹配或仅用内容 ID 合并重复实例；比较公开观察、完整候选/绑定、暂停/终局及适用事件/RNG。隐藏状态只进入诊断，不进公开输入。

优先接通头槌决策与真实随机 case，包括初始洗牌/弃牌重洗。核对参考普通顺序模式和源版本差异；按已有约束处理明确派生差异，不改参考游戏效果、不调用 base 函数制造参考答案、不补抽/换 seed。窄源裁决由负责人确认；未具备双侧比较的项如实标 blocked，不算 passed，但继续其他能力接入。

命令成果：

```powershell
pwsh -File tools/differential/test-env.ps1 -Suite regression
dotnet run --project tools/differential -- test --suite regression --output artifacts/environment/tests/regression
```

以上是待实现入口。DIFF-01 验收至少证明实际双侧执行与首个差异定位，以及有限的缺 case/unsupported/参考缺失失败反例；随后立即转 DIFF-02，不继续泛化测试平台。

### DIFF-02：整局、覆盖与候选结算

把 `run` 从人工清场探针升级为解析角色/进阶/seed 的正常原版流程，旧探针保留明确受控身份。随 A/B 功能增加 regression；实现 `ironclad-run`、`full-singleplayer` 严格 suite 和 `verify --manifest`，不等全内容完成后才补对拍。

核对现有 1567 候选分母及 32 项待核对可达性，冻结 source/reference 实际摘要及排除理由；数字只作起点，更新须由源证据生成。覆盖只能来自本轮预登记且实际执行的 case 和有效产物，不扫描历史 JSON 字符串算覆盖。首个差异保存最后一致边界、动作前缀、两侧路径/值、事件/RNG前缀、源定位和复现命令。

最终矩阵沿既定合同：五角色 × 进阶 0/5/10 × 8 个 `ENV-FINAL-{Character}-{Ascension}-{i:02}` seed，共 120 对；每 case 120 秒/20000 外部决策/100 层保护，总 14400 活动秒。超限不伪装自然死亡。仍须每角色完整胜利与必需机制/房间证据，不能以 120 次早死关闭完整环境。最后提交 manifest、分层覆盖、未解决差异、公开胜负轨迹引用和 Release 成本；所有数字绑定本轮 run_id，负责人关闭。

## 5. C：NET-01/02，完整公开出口

### NET-01：同正式工厂和协议 0.2

按 [协议第7节](net-the-spire/protocol.md#7-env正式环境的02扩展)实现正式 Host 的角色/进阶/范围配置，start 接受每局游戏字符串 seed 并返回实际 seed。保留旧 0.1 数字 seed 行为；C#、Python codec/schema、载荷摘要及正反例同批更新。复用 A 配置好但未 Start 的 Session，不另 `new Session` 换回默认 RNG，不执行两次初始化。

描述/目录/Profile 必须反映实际构建；seed 不进入静态规则/目录身份或模型特征。错误身份/seed 在创建启动前拒绝；同 request 重发返回原 seed/session/snapshot。同 Host 连开不同 seed 能成立，相同 seed/config 独立会话不污染。发布 UTF-8 NDJSON，stdout 只写协议。

### NET-02：随内容扩展全部可决策场景

沿 A 的实际流程公开地图、长期牌组/资源、奖励/选牌、商店、药水/遗物、事件及战斗等可见事实和合法操作；候选与绑定来自同一 Engine 稳定边界，不在 net 重算玩法。抽牌堆仅发布当前已知实例和绝对位置，重洗撤销失效知识；不增加 known_top、隐藏牌序、内部 RNG/trace 或 AI 历史补偿。优先复用既有通用 wire 结构，确有契约缺口再明确版本化。

关键交付是 Python 公开客户端经正式 Host 正常开局并完成完整 Ironclad，后续各角色胜负轨迹；期间所有实际决策均可表达，重发/过期候选/容量与未知内容正确处理。net 的局部检查绿色不能代替这条真实公开运行证据；与 B 对照两条入口的同配置/同 seed 实际结果。

## 6. 后排任务：真实客户端与指定 mod

### CLIENT-01：原版候选的真实客户端核对

原版候选稳定后再派。固定真实游戏版本/构建、配置、解锁、seed 与语义选择，获取正常开局到终局及重点机制的可复现记录；以 B 的既有记录/首个差异规范导入比较。不能要求私有实现布局完全相同；必需公开状态、选择、暂停、终局和可取证的规则/RNG时序需对应。可先用实际录制记录，不把完整 UI 自动化平台作为前置。

交付可重复采集/导入说明、双侧结果和具体差异。没有匹配客户端、版本或足够证据时明确 blocked/未验证，不能把源码对照写成客户端已测；按已有 ENV 范围，客户端驱动适配单独派单，不混入 A/B/C 当前编码任务。

### MOD-01：一个具体 mod 的端到端支持

由用户先指定 mod 名称、版本、内容范围和真实客户端记录条件。实现内容包及可复用 DSL 规则库，沿相同生产接口加载，显式记录 mod 包身份、游戏/mod 版本、依赖与加载顺序。一个 mod 先完成从加载、实际决策到终局的闭环，再推广其他包；不要求未知 mod 自动理解/迁移。

对照**真实尖塔加载同一 mod**的表现；可达资源、随机/选项/机制及公开知识纳入比较，参考模拟器仅在明确支持该 mod 时提供辅助证据。原版回归与 mod case 同时保留；运行时变化不得污染原版规则身份。遇到环境依赖/外部输入记录其条件与比较边界；core 缺口仍交负责人，不自行解冻。

## 7. 每批交接与用户验收

每个机制族/阶段只提交一份综合交接到 tofix，追加本线进度；记录可运行的新能力、负责文件、配置/身份、命令及返回码、实际双侧通过/blocked/失败数、首个差异和剩余阻塞。不要每张牌建报告，不把旧测试刷新写成主要成果。已解决项由负责人核对后归档，未完成项不归 archived。

负责人先看实际交付：**公开入口能做什么、正常 Run 走到哪里、独立对拍证明了哪些新增行为**；再核对代码/范围/测试。可交付阶段与整个项目完工分开；范围/门槛变更、核心语义升级、参考裁决和父项关闭由用户/负责人决定。
