# 内容、共享规则与引擎怎样协作

文档类型：解释（Explanation）。本页说明为什么按领域写 DSL，以及怎样避免开发时反复翻大文件。具体操作见[内容扩展](../how-to/extend-content.md)，准确调用见[共享操作参考](../reference/operations.md)。

base 的职责是定义游戏模型和规则，Engine 的职责是编译、保存通用状态并执行同一 IR。Host 负责 IO、会话和公开适配。将效果搬到包外 C# 并继续调用，会让内容维护重新依赖编译器分支，因此不属于纯 DSL 内容开发。

完整 DSL 可以声明实体、集合、过程、事件、订阅、动作、投影和模板。具体内容文件可声明完整 DSL，以模板作用域隔离独有过程、监听和私有实体。简单内容仍可只用 `use`，参数受模板类型与边界约束。只有真正共用的操作进入领域规则库，不增加第二个效果解释器。

```mermaid
flowchart LR
    Source[匹配版本的原版依据] --> Contract[领域行为要求]
    Contract --> Shared[完整 DSL 共享规则]
    Shared --> Config[独立内容模块：定义、行为、私有状态]
    Config --> Index[显式领域索引]
    Index --> Engine[Engine 编译与 Session]
    Engine --> Public[同一公开目录、候选与观察]
```

静态源目录与可执行内容目录回答不同问题。源目录说明原版有哪些对象、来自哪里、资格是否审阅；非空 definition 说明有 DSL 定义。定义存在仍不能代替行为执行结果、原版独立比较和正常流程验证记录。教学内容可以有自己的 ID，但不能冒充一个原版源对象。

状态按生命周期归属。永久状态归 Run，战斗副本归战斗，临时绑定归调用帧；具体模型仍需对应机制的 DSL 定义。内容只描述自己的资格、参数和顺序，获得／移除、牌区迁移、伤害与死亡等共享操作负责完整不变量。直接写一个字段通常不能替代完整领域行为。

显式索引使文件新增和启动顺序可审阅。文件先合并声明再绑定，跨文件前向引用可用；namespace、版本、重复声明、循环和源位置由通用加载器处理。文件名与目录重命名不应改变内容 ID。

遗物与Power在流程中的职责相似：它们持有实例状态，监听主流程提供的通知和修正阶段。通知回答“发生此事后做什么”，可以产生效果；修正回答“当前计算如何变化”，只返回计算值。伤害、费用等主流程不需要知道具体能力，而是通过同一阶段征询有效实例；力量Power与StrikeDummy遗物都能在伤害加法阶段贡献结果。

订阅定义在组包时建立，持有实例在局内获得或施加时创建。instances把定义绑定到当前有效实例，instance_order表达实际持有顺序，priority表达明确的早晚阶段；不能把模板展开或文件组合顺序当作遗物获得顺序。通知和修正共用实例快照及执行前有效性检查，副作用仍由原Session栈执行，修正受到pure约束。能力特有状态归对应实例或附属实体，不靠不断扩充公共Relic字段让主流程猜效果。具体写法见[监听编写指南](../how-to/write-effect-listeners.md)，精确语义见[统一约定](../../../design/mod-the-spire/effect-listeners.md)。

内容模块拥有自身行为与私有状态，共享操作拥有跨内容的不变量。SelfFormingClay的施加收益归遗物、兑现与移除归Power；两者共用ApplyPlayerPower／RemovePower和回合通知，调用方无需知道它的具体实现。新增内容仍需显式索引、来源与公开登记；该边界减少玩法散落，不消除所有登记成本。

降低阅读成本依靠准确资料：先读任务对应的一页指南和一个共享操作，再按 catalog 定位一个源文件／方法。旧 C# 只在验证历史顺序或寻找回归意图时局部读取。skill 提供这条路由，不保存另一套玩法约定或当前状态；它也不保证 DSH 自动发现项目目录。
