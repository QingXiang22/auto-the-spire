# 内容、共享规则与引擎怎样协作

文档类型：解释（Explanation）。本页说明为什么按领域写 DSL，以及怎样避免开发时反复翻大文件。具体操作见[内容扩展](../how-to/extend-content.md)，准确调用见[共享操作参考](../reference/operations.md)。

base 的职责是定义游戏模型和规则，Engine 的职责是编译、保存通用状态并执行同一 IR。Host 负责 IO、会话和公开适配。将效果搬到包外 C# 并继续调用，会让内容维护重新依赖编译器分支，因此不属于纯 DSL 内容开发。

完整 DSL 可以声明实体、集合、过程、事件、订阅、动作、投影和模板。Spire 内容配置只允许调用 DSL 模板的 `use`，参数受模板类型与边界约束。需要一种新的共享效果时，先在领域规则库实现，再用内容配置组合，不增加第二个效果解释器。

```mermaid
flowchart LR
    Source[匹配版本的原版依据] --> Contract[领域契约]
    Contract --> Shared[完整 DSL 共享规则]
    Shared --> Config[Spire 内容 use 配置]
    Config --> Index[显式领域索引]
    Index --> Engine[Engine 编译与 Session]
    Engine --> Public[同一公开目录、候选与观察]
```

静态源目录与可执行内容目录回答不同问题。源目录说明原版有哪些对象、来自哪里、资格是否审阅；非空 definition 说明有 DSL 定义。定义存在仍不能代替行为见证、原版独立比较和正常流程证据。教学内容可以有自己的 ID，但不能冒充一个原版源对象。

状态按生命周期归属。永久状态归 Run，战斗副本归战斗，临时绑定归调用帧；具体模型仍需对应机制的 DSL 定义。内容只描述自己的资格、参数和顺序，获得／移除、牌区迁移、伤害与死亡等共享操作负责完整不变量。直接写一个字段通常不能替代完整领域行为。

显式索引使文件新增和启动顺序可审阅。文件先合并声明再绑定，跨文件前向引用可用；namespace、版本、重复声明、循环和源位置由通用加载器处理。文件名与目录重命名不应改变内容 ID。

降低阅读成本依靠准确资料：先读任务对应的一页指南和一个共享操作，再按 catalog 定位一个源文件／方法。旧 C# 只在验证历史顺序或寻找回归意图时局部读取。skill 提供这条路由，不保存另一套玩法契约或当前状态；它也不保证 DSH 自动发现项目目录。
