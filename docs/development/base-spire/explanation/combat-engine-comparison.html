两边分别怎样运行

sts2-sim：RunDriver让CombatRoom准备本场状态；CombatEngine驱动阶段。Commands调用Hook，具体模型覆盖方法响应；模型再调用Commands产生嵌套效果。可变状态在Run、Combat和内容实例中。

base-spire：Host提交公开动作，Session执行已编译DSL。Run和combat领域过程发布通知或征询纯修正；内容订阅按有效实例响应，调用同一领域过程。暂停与恢复沿同一个通用执行栈继续。

迁移应保留命令输入、阶段、实例寿命与随机消费；C#模型名与DSL模板名无需一一对应。核心可以继续保持通用。

阅读开始阶段时注意什么

源AfterPlayerTurnStart会在内部依次调用Early、普通和Late。只搜索CombatEngine中是否直接出现Late，会错误漏掉这一层转发。

图中的起手抽牌是fromHandDraw=true；效果抽牌是另一路资格。已有NoDraw相关迁移不能替代所有回合站点的符合性验证。

出生时先抽HP，之后的槽位排序与入场效果各自有顺序。用“生成一个怪物并立即做完全部初始化”的万能过程，会丢失批量编队所需的阶段。

为什么Orichalcum需要两个阶段

参考先保存“本回合结束早期是否为零格挡”，再允许其他Early效果加格挡，最后兑现6点。当前DSL保存每个Orichalcum实例的早期资格，Plating加格挡后仍兑现6点。

虚无耗尽与普通耗尽共享完整命令，但原因不同。DarkEmbrace对虚无延迟抽牌，CharonsAshes忽略该原因并即时伤害；不能统一延迟所有耗尽效果。

图仅表达已核对的主要路径。召唤、复活、额外回合和角色专属阶段仍须按各自实际支持核查，不能从主路径图推导已全部实现。

顺序、计算与副作用各自负责什么

通知允许后续效果与嵌套决策；pure修正只能计算返回值。某些源Hook在纯计算中记录实际修正者，随后执行它们的After通知，这是Artifact等内容所需的两个独立步骤。

source常用路径与ShouldClearBlock特殊路径不同。参考对遗物／牌等资格仍保留声明偏离，不能把它概括为所有模型都在每次调用前严格验证库存。

Attack表示整次攻击，Hit表示一次命中；两者的前后边界不相同。现有ExecuteAttack已是值得复用的基础，旧模板不应另造循环攻击语义。

怎样复用Power操作

新建、叠加、直接增减已共用一次变更流程，保留不同入口的通知条件。扩展修正时继续复用上下文，避免双重计算。

Artifact将负面变化改为0，并在修正后扣一层；即使未产生新Power，消费逻辑仍可能发生。因此只订阅PowerCreated或PowerApplied不足以实现它。

private状态继续归模块：Vigor保存本次Attack及开始层数，DarkEmbrace保存虚无耗尽次数。共享生命周期只管理共同不变量，不把全部内容计数搬进Power公共字段。

哪些逻辑适合成为共享操作

Obtain、Replace、Melt是库存操作，负责位置、来源袋和回调顺序；拾取效果与持续效果由实际遗物定义处理。模板只复用相同阶段与同构正文。

Counter并不代表所有遗物共享同一寿命。Nunchaku跨战保留，Kunai／Shuriken有回合重置，首次受伤遗物有每战状态；按具体实例维护它们。

no-energy-gain是本地已登记Power但未按当前源类直接对应，应单独说明用途与来源。源码条目、可执行定义、组件符合和正常可达是不同判断。

人工复核的顺序

先查源调用方，确认阶段、参与者与结束门禁；再查Hook及具体内容正文；最后核对DSL共享过程、订阅签名、实例顺序与私有状态。相同方法名、定义数量或单个模板测试都不能替代组合行为比较。
