# 开发角色、房间与完整 Run

文档类型：操作指南（How-to）。适用于角色／进阶、正常开局、地图、战斗／商店／营火／宝箱／事件、奖励、永久状态、Ancient、跨幕与终局。当前 SetupDevelopmentDraw 仅创建开发玩家和三张牌；以下是恢复完整 Run 的开发方法，不提供已实现的旧 SinglePlayer 工厂或房间 C# 接口。

先查[领域参考](../reference/domains.md)和原[完整环境合同](../../../design/environment-completion-and-differential-v1.md)。按共享状态和生命周期的依赖恢复一个完整纵向流程；不从固定 seed 的首错临时复制一个房型实现。

## 定义角色、进阶与正常开局

在 characters 的内容配置保存角色身份、源池归属及参数，在 run 的 DSL 初始化流程创建权威角色／永久牌组／遗物／药水／资源与源随机状态。区分基础角色配置、进阶修正和 Neow 等正常开局选项。

获得初始物品是否触发生命周期、随机队列的生成顺序、初始资源和跨幕持久字段均以源契约固定。五角色专属资源分别依赖共享机制；一种角色能开局不代表其他角色可玩。没有 Neow 和真实初态的开发开局不能冒用正常 scope。

## 建地图与房间访问生命周期

maps 保存图结构、节点／边、原始节点类型与访问历史；run 保存当前幕、旅行／访问／待选择等权威状态。问号节点判定的实际房型与原节点类型分开存储，不覆盖地图身份。

先定义选点守卫、进入房间、活跃访问、关闭访问和返回旅行的共享操作。房间自身只拥有自己的阶段、选项、资格与独有内容。公开候选必须来自同一状态机，不能由客户端发任意节点／房间字符串跳转。

源地图生成、问号赔率、事件／遭遇队列和 Ancient 分配分别消费明确随机流。静态 act-plan／act-pools 只保存来源，不能靠 JSON 中的效果字段执行整局。

## 实现各类房间

| 房型／内容 | 先定义的局部行为 | 必须区分的结果 |
| --- | --- | --- |
| 战斗房 | 从永久牌组构建战斗副本，实例映射、源随机与战斗上下文 | 真实胜负后收尾、长期状态提交一次、奖励进入，最后一击余效不丢 |
| 商店 | 源资格、货架生成、价格／折扣、支付／购买、删牌与离店 | 不可支付／满容量不丢货、消费一次、遗物参与者及永久牌组结果 |
| 营火 | 源选项资格、休息／升级及遗物增减选项 | 没有候选的处理、一次选择、合法离场和永久写回 |
| 宝箱 | 资格／开箱、遗物生成与获得、领取或跳过 | 完整源池不缩、重复领取拒绝、获得钩子与访问关闭 |
| 普通事件 | 访问初始化、页面、选项资格、支付／效果和关闭 | 每个有效分支、无效支付、状态携带、选择暂停与取消 |
| 事件子战斗 | 保存父访问、建立子战斗、完成后的返回规则 | 返回原页／继续事件或直接结束，父状态与未完选项不丢 |
| 先古之民 | 幕进入与选项、专属奖励、持续效果及来源 | Neow 与后续 Ancient 分列，选择影响后续真实战斗 |

按上述完整访问链建立规则和契约，再用事件／房型内容配置组合。不存在一种可将所有房间任意字段修改并统一 Close 的万能操作；关闭访问不等于完成支付、获得、子战斗结算或终局。

事件资格是执行内容选择的规则，不是静态 catalog 字符串。保留 act-local／shared／Ancient 分类、未访问优先、耗尽回退和源顺序；不能恒 true 或删未迁移事件以推进某个 seed。

## 生成并结算奖励

开发包已恢复 Monster 金币的最小领取链：胜利后 `Player.Room="rewards"`、`GoldRewardPending=true`，`GoldRewardAmount` 保存 10..20 的金额，金币暂不增加。公开候选 `ClaimDevelopmentGoldReward` 领取保存金额；`CloseDevelopmentRewards` 关闭界面，未领取时即跳过。领取后仍需关闭，才能开始下一开发战斗或进入营火。金额仅在生成时抽一次，失败不给奖励；准确参数和边界见[操作参考](../reference/operations.md)与[奖励契约](../../../design/mod-the-spire/combat-rewards/spec.md)。这不是正常 Run 奖励，也没有卡牌／药水／遗物条目或原版随机布局。

rewards 拥有奖励容器和待领取状态；卡牌／遗物／药水的完整获得操作仍归对应领域。明确生成候选、随机权重／升级／稀有度、显示、领取／跳过、满容量处理、未选实例清理和最终关闭顺序。

卡牌选择、升级／变换、药水满栏以及遗物替换可以暂停，但续接不能重新抽样、重复支付或提前关闭访问。战斗／事件／商店调用同一获得操作，不各自创建永久对象。

## 保存永久状态并推进到终局

在 Run 模型中唯一维护永久 HP／最大 HP、金币、永久牌组、物品实例和跨房状态。战斗映射保存哪些变化可回写、何时回写，Fatal、失败、取消与重试分别约定。不要同时更新战斗镜像与长期字段两次获利。

幕转换明确关闭 Boss 奖励、清理幕内寿命、保留长期实例、生成／切换队列、进入 Ancient 和下一幕地图。正常最终胜负必须来自 DSL 终局规则，在待结算余效和选择处理之后发生。受控强制清场或直接注入下一幕不能替代真实跨幕验收。

## 验证一个可观察的流程

先让一个完整访问链可执行：正常初态→公开选点→实际房间／战斗→领取或跳过→长期状态写回→回到地图。记录每个稳定边界、seed／scope／构建身份、随机消费和公开结果，再做独立参考逐步比较。

随后验证失败／死亡路径、其他房型、Boss 奖励关闭和跨幕。原 ENV 里完整 Ironclad、多角色／进阶、四幕与最终矩阵保持原标准，不能由一个正常返回地图的案例关闭。按[机制迁移](migrate-mechanism.md)维护共享操作与检查去向。
